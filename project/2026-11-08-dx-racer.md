## 2026-11-08 — Racer 1: the scanline road (leaf CPZAuJ, agent racer14)

### What I built

The game is **Switchback**. The road is a 256x256 BG image (`tools/road.py` → `assets/bg/road.png`, 127 unique tiles): 96 rows of sky, then 80 road strips (horizon-narrow to bottom-wide) in each of two stripe phases. Every screen line shows one BG row: SCY picks the strip (depth), SCX shifts it for curves and steering.

- **The interrupt** (`src/road.asm`, `StatHandler`): STAT mode 0 (HBlank) on every line. The code sits in the $48 vector itself, running on past $50 and $58 (no `jp`, 4 M-cycles saved a line), so the timer interrupt is unavailable. I edited the starter's `music.asm` to drop its timer vector and `ASSERT song_theme_TIMER == 0`. It reads LY, indexes a page-aligned table (the entry at index L holds line L+1's values; line 0's values sit at index 255 and VBlank writes them), and writes SCX and then SCY. That costs 42 M-cycles a line.
- **The tables** are double-buffered (4 WRAM pages). VBlank swaps them only when the main loop has finished the back buffer.
- **Hills and curves are precomputed** by `tools/tables.py` into `src/road_tables.asm`: 32 hill profiles, giving the strip per line with horizons spread from line 22 (steep climb) to 102 (crest), and 32 curve profiles, giving the pixel offset per line. There are also 32 stripe-phase tables (strip → BG row). The per-frame work is two loops run from WRAM with their immediates patched (self-modifying), so no register goes to a constant. The vertical pass costs 18 M-cycles a line and the horizontal pass 26.
- **Driving** (`src/drive.asm`): A/Up accelerates, B/Down brakes, Left/Right steer, and curves push the car outward. A looping demo track eases the curve and hill levels toward each segment's targets. The car is a placeholder 4-object sprite.

### Criteria, with the commands that show them

1. **The road curves and climbs.** In this filmstrip, frame 120 shows a climb (high horizon) with a bend, 300 a left bend, and 420 a drop (low horizon over a crest):
   `gbcli run build/racer.gb --session drive --frames 480 --keys 'A@0' --filmstrip build/drive.png --every 60 --checkpoint drove`
2. **Every scroll write lands in HBlank.**

   > **Correction (racer 2, same day):** this proof started from a checkpoint at frame 30, so it skipped the first frame with the LCD on. That frame had a late write. The startup enabled the STAT interrupt before `MusicInit`, so an HBlank request left pending fired at `ei`, mid-line. A run from boot catches it at frame 7, line 8. Racer 2 fixed it by enabling STAT only from the first VBlank. The handler measured below was also replaced in racer 2 (a RAM handler with patched immediates, and the sky lines skipped). Racer 2's section has the current proof, which runs from boot.

   I set breakpoints on both write instructions, conditioned on the PPU *not* being in mode 0, then drove a 900-frame steering run. Neither fired, so all 259,200 SCX and SCY writes executed in mode 0:
   ```
   gbcli run build/racer.gb --session proof --frames 30 --checkpoint started
   gbcli break StatHandler+9  --if '([rSTAT] & 3) != 0' --session proof
   gbcli break StatHandler+13 --if '([rSTAT] & 3) != 0' --session proof
   gbcli run --session proof --at started --frames 900 --keys-file tools/steer.keys --frame-budget --profile --top 8
   → stop budget_exhausted kind=frames … frame=930   (no breakpoint stop)
   ```
   The positive control (same break, `== 0`, in session `ctl`) stops at once: `stop breakpoint id=1 pc=$0051 … ly=7`, with `[rSTAT] & 3` reading 0. `--raster` agrees on the line: each line L carries the writes for L+1, at `into=716..814` ticks (358-407 dots). That is after mode 3 ends whenever a line has at most 9 objects (172 + 7 + 9×11 = 278 dots), and before the line's end at 456 dots.
3. **No lag frames while steering.** Same run: `frame_budget frames=900 lag=0 active_min=49372 active_max=54860 active_mean=50471.5`. That is 72% of a frame on average and 78% at worst, leaving about 15,000 T-cycles (22%) at the worst frame for the game. The profile, per frame, has the HBlank interrupt at 24,190 T (34%), the horizontal loop at 9,070 T exclusive, the vertical loop at 6,800 T, the rest of ComputeRoad at 3,230 T, and hUGE at about 1,450 T.
4. Also clean under `gbcli build --gbc --out build/racer-gbc.gb`, run with `--model gbc`.

### Where gbcli helped (saved real time)

- **The link error for a full bank** told me exactly what was wrong and both ways out. I would otherwise have lost time in the .map file. `gbcli build`: `the header names no MBC (cartridge type $00) … placed a section past bank 1: "song_theme Song Data" in bank 2` with `remedy: shrink the sections … or name an MBC in the header (the byte at $0147 …)`. I moved the 8 KB of profiles to ROM0.
- **The duplicate-label diagnostic** names both include chains (`from file=…road.asm` / `also … from file=…drive.asm`), so the fix (split the generated constants from the data) took a minute.
- **The images pipeline** accepted a 256x256 map with 127 unique tiles and handed me `RoadTiles`, `RoadTilemap`, `ROAD_TILES` and the GBC variants with no configuration. The `--gbc` build ran on the first try.
- **Conditional breakpoints with `[rSTAT]`** made a real "never outside HBlank" proof possible in one run. This was the most valuable thing of the session.
- **`--profile` and `--frame-budget` in the same run as the keys file** gave the cost picture in one command.

### Stumbles, costliest first

1. **`--raster` can't say whether a write was in HBlank (about 15 minutes).** The obvious command, `gbcli run --session drive --at drove --frames 1 --raster`, prints `into=` ticks per write and then `raster_unsupported feature=ppu_dot` and `raster_unsupported feature=ppu_mode_events`. I expected a mode column, or the line's mode-3 end, since the help sells `--raster` for exactly this check (`gbcli help traps` says to "keep the write within that mode"). Without one, I had to compute the mode-3 length by hand from object counts and SCX%8, which is only a bound. Then I found the breakpoint-on-STAT trick, which is exact but not documented anywhere as the way to check this. **Ask:** a `mode=` field on each `raster_write` (or `mode3_end=` on each `raster_line`), or a recipe line: "Did my scroll write land in HBlank? `gbcli break WRITE_PC --if '([rSTAT] & 3) != 0'`, then run".
2. **The profiler names a routine by an unrelated symbol (about 5 minutes).** `--profile` printed `routine name=end_zero bank=0 addr=$C504` for my `VLoop` (WRAM code in a `LOAD` block). The `.sym` has `00:c504 RoadLoops`, `00:c504 VLoop` and `00:c504 end_zero` (a hUGEDriver symbol), and the profiler picked the driver's name. I expected the most specific code label, or all of them. I worked it out from `build/racer.sym`.
3. **Every Bash call needs `--dir examples/racer` (minor).** The worktree's one-command-per-call rule means no `cd`. `gbcli build DIR` takes the project, but `run` needs `--dir` and then reads the ROM path relative to the cwd, not to `--dir`: `gbcli run build/racer.gb --dir examples/racer --session pathtest --frames 1` gives `rom_unreadable: can't read ROM …/agent-a55789c02ddb2ff1a/build/racer.gb`. I expected `--dir` to anchor both. It works; it's just noisy.
4. **`run` frame budget and the boot lag (minor).** The first `--frame-budget` (from boot) reported `lag=6` for frames 0-5. That is my startup with the LCD off, clearing WRAM, and it is correct behavior, but the summary row reads like a failure. I re-ran from a checkpoint after startup. A note that the LCD-off startup counts as lag, or a `--since`-style exclusion, would save the double take.

### Missing

- A PPU mode (or dot) on raster writes: see stumble 1. `gbcli gaps` lists it already.
- Nothing in `gbcli help` about the HBlank interrupt pattern itself (STAT mode 0 source, entry latency, the table-index-is-next-line convention). Pan Docs covers the hardware; a recipe would have saved re-deriving it.

## 2026-11-08 — Racer 2: the race (leaf pYkhXU, agent racer14)

### What I built

A race against the clock. A 3 s countdown starts it, and the player then has 50 s to drive one lap: 16 segments, 10,000 depth units, about 42 s flat out. Crossing the finish wins; the clock reaching zero loses, and START restarts. `wState` holds the state for scripts: 0 READY, 1 RACE, 2 WON, 3 LOST.

- **Objects** (`src/objects.asm`). There are 10 rival cars (at 2.5 depth units a frame against the player's 4) and a tree every 96 depth units, alternating sides. Each has a depth and a lane. A table maps depth to a road strip, and a bisection of this frame's hill profile maps the strip to a screen line (an object behind a crest is hidden). The line's SCX in the back buffer, plus the lane's offset at that strip, gives x. The strip picks one of four pre-scaled frames (`rival.24x16.png` and `tree.8x32.png` sheets). Objects land on exactly the road the HBlank interrupt draws next frame, curves and hills included.
- **Collisions**: a rival level with the car slows it to 24. A tree stops it dead for 45 frames and throws it back toward the road. On the grass, the speed falls to 24.
- **HUD**: one window row along the bottom (font tileset `assets/tiles/font.png` from `tools/font.py`, with an rgbasm `CHARMAP` in `include/charmap.inc`), copied in VBlank.
- **Placeholder art** comes from `tools/sprites.py` (car, rival at four sizes, tree at four sizes).

**The scanline engine changed, twice, because the race made it fail:**

1. **Frame time.** With objects added, the worst frame hit 97.3% of the budget. Two fixes:
   - Rivals now share one distance travelled. At most one rival is in view, so there is no per-rival loop.
   - The HBlank interrupt is off over the sky. VBlank disables it in IE and arms the timer (16 kHz, `TimerStart` table per horizon) to fire 4 lines above the horizon. The timer handler waits for an OAM-scan mode, then clears the pending STAT request and enables it.
2. **Writes outside HBlank.** The breakpoint proof from racer 1, rerun on a full race from boot, caught two real late writes:
   - the startup one (see the correction in racer 1's section);
   - an SCY write in mode 2 of line 121 at frame 873. Line 120 carried 10 objects (car, near rival and tree, then 4 + 4 + 2), so HBlank was too short for a handler that wrote SCY 144 dots in.

   The fix is a RAM-resident handler (`StatHandler` in a `LOAD` block) that writes SCX and SCY from patched immediates first: done 92 dots after the interrupt, plus at most 20 for the interrupted instruction. It then patches the immediates with the line after next. It is paired with narrower sprites (car 3 objects, rival 3, tree 1 per line), so the car's lines hold at most 7 objects and HBlank lasts at least 120 dots. The steepest climb's horizon also went from line 22 to 40 (`CLIMB_TOP`), which caps the road at 104 lines.

### Criteria, with the commands that show them

1. **A scripted run completes the lap and wins; another loses.** `tools/driver_bot.py` drives the lap closed-loop through gbcli: every 6 frames it reads `wPlayerX` and steers toward the center line. It writes the inputs as `tools/win.keys`, which replays in one run:
   ```
   python3 -I tools/driver_bot.py /path/to/gbcli          → state 2 after 2688 frames
   gbcli run build/racer.gb --session race2 --keys-file tools/win.keys --until '[wState] == 2' --frames 3000 --frame-budget --read '[wTimeSec]' --read '[wBumps]' --read '[wCrashes]'
   → stop predicate … frame=2686; wTimeSec=7 (BCD: 7 s left), wBumps=1, wCrashes=0
   gbcli run build/racer.gb --session lose2 --keys-file tools/lose.keys --until '[wState] == 3' --frames 3300 --read 'u16[wD]' --read '[wCrashes]'
   → stop predicate … frame=3128; wD=2518 of 10,000, wCrashes=24
   ```
2. **No lag frames in the busy stretch.** The same win run, `--json` to a file and summarized by `tools/budget_summary.py` (which skips the 7 startup frames, LCD off, that the budget counts as lag): `frames 2677 after skipping 10: lag 0; active max 65144 (92.8%) at index 2120, mean 57473 (81.8%)`.
3. **Writes in HBlank, rechecked from boot** (racer 1's criterion, since the engine changed). `gbcli break StatScxWrite --if '([rSTAT] & 3) != 0'` and the same on `StatScyWrite`, then the full win run above. Neither fired over 2,686 frames.
4. **At most 10 objects a line.** At the moment of a rival bump (`--until '[wBumps] == 1'`, then one more frame), `gbcli view oam --session busy` shows car, rival and tree on screen, with `dropped_by_line_limit=0` on all 40.

### Where gbcli helped

- **Conditional breakpoints on `[rSTAT]`, again.** They found two real bugs I would never have seen in screenshots, because a mode-2 write of the right value looks identical. The single most valuable thing gbcli gave this game.
- **Held keys persist across runs, and runs are deterministic.** That made a closed-loop bot in 60 lines of Python possible, and its log replays exactly. It produced a winning lap on the first try.
- **`--profile` per frame from a checkpoint** (`--at f742 --frames 1 --profile`) pointed straight at the worst frame's cost: a steep climb's 115 road lines.
- **The images pipeline's frame lists** (count, then y/x/tile/attr per object, empty objects dropped, mirrored halves deduplicated with X flip) meant no OAM layout code for the sheets.

### Stumbles, costliest first

1. **The racer-1 proof had a hole, and nothing in gbcli pointed at it (about 40 minutes, counting the redesign).** I proved "every write in HBlank" from a checkpoint after startup. That was my mistake, not gbcli's. But a raster or mode view would have shown the frame-7 write the first time.
2. **A breakpoint condition on `[rSTAT]` can fail the run with `unsupported` (about 10 minutes).** `gbcli run --session race2 … --json` exited 5 with `unsupported: condition of #2: unsupported (SideEffectFreeIo): … PPU registers are unavailable while mode-3 cycles are batched`. Yet `gbcli show` afterwards said `stop breakpoint id=2 pc=$0076 … ly=121` and `ppu … mode=oam_scan`. So it was a real stop at a real late write, reported as an error. I expected either a clean breakpoint stop or a clear "can't evaluate here". Getting both left me unsure whether the run had stopped or crashed. It also raises the worry that a write *during* mode 3 might come back as this error rather than a stop. It is at least loud, never a silent pass. `gbcli gaps` now lists `side_effect_free_io count=2`.
3. **A short run with a long keys file prints every unapplied key twice (minor, but it buries the stop).** `gbcli run … --keys-file tools/win.keys --frames 30 --checkpoint started` printed a 150-key `warning:` line and then 150 `key_unapplied` rows. I expected one summary line (`152 key events after the stop, first RIGHT@348`).
4. **`gbcli build DIR --session S --restore C` looks for the session in the cwd, not in DIR.** `gbcli build examples/racer --session race2 --restore started` gave `no_session: no session "race2"`. `--dir examples/racer` fixes it, but `build` takes DIR as the project, so I expected sessions to be found from it too.
5. **The profiler names the STAT vector `VBlankVector+$8`** (`routine name=VBlankVector+$8 bank=0 addr=$0048 calls=118`), because the vector holds a `jp` with no label. A symbol for the hardware vectors (`INT_HANDLER_STAT`) would read better. Minor.
6. **`--frame-budget` counts the LCD-off startup as lag**, so every from-boot run reports `lag=7`, and the summary's max is a startup frame. I wrote `tools/budget_summary.py` to skip them. A `--skip N` or a `--since` checkpoint that also trims the budget would remove the script.

### Missing

- A per-line object count in `gbcli view oam` (the max per line, not only `dropped_by_line_limit`). Staying under 7 is a timing constraint here, not just the hardware's 10.
- A frame-budget summary that excludes LCD-off frames.
- Still: a PPU mode on raster writes.

## 2026-11-08 — Racer 3: art, music and sound (leaf troaCp, agent racer14)

### What I built

- **Art, all generated** by `tools/make_assets.py`, which runs every generator in order:
  - `palettes.py` writes `assets/palettes.txt`: a dmg line and two named palettes.
  - `road.py` draws the road BG; `title.py` the 160x144 title screen (sun setting behind mountains, road, the name in doubled glyphs, PRESS START).
  - `sprites.py` draws the car, the rival at 4 sizes and the tree at 4 sizes; `font.py` the HUD glyphs.
  - `songs.py` writes both songs; `tables.py` the engine's tables.

  Colors live in one file, `tools/colors.py`. The two backgrounds are **indexed art**, drawn in the 4 DMG shades and colored on the GBC by assigned palettes: road is pale sky, green grass, gray road and red rumble; title is a cream, orange, purple and near-black sunset. The sheets are color art, with 3 colors each.
- **A title screen** (`Title` in main.asm, `wState` 4). START goes to the race, and START after a result goes back to the title.
- **Music** as gbcli song text: `title.song` (all four channels, an arpeggio chord bed, bass, lead and drums) and `race.song` (channels 1, 3 and 4: bass, lead, drums, 4 orders). Both are generated from phrase lists in `tools/songs.py`.
- **Effects** on channel 2, which the race song leaves empty and `SfxInit` mutes in hUGEDriver (`src/sfx.asm`):
  - an engine drone whose pitch follows the speed (70-134 Hz, updated without retrigger);
  - countdown beeps and a GO tone;
  - a rival bump and a tree crash;
  - the finish jingle (the lap sound, since there is one lap) and a time-up phrase.
- **ROM had to shrink** to fit `--gbc` in 32 KB. Curve profiles are now mirrored (17 instead of 32, with a patched `cpl` in HLoop), the stripe tables moved to ROM0, and the backgrounds became indexed art (no second set of GBC tiles).

### Criteria, with the commands that show them

1. **Every PNG is produced by a script and regenerates byte-identical.** `shasum` over all six PNGs, `palettes.txt`, both songs and `src/road_tables.asm`, then `python3 -I tools/make_assets.py`, then `shasum` again: identical (road.png `b91dcbaf…`, title.png `d8053d6d…`, car.png `7b7b2c06…`, rival `1f087ea7…`, tree `059e8ff4…`, font `4c305971…`).
2. **Music and effects show in the audio views.**
   - Title theme: `gbcli run build/racer.gb --session audio --frames 300 --piano build/title-piano.png --checkpoint title`.
   - Race start: `gbcli run --session audio --frames 360 --keys 'A@0 START@2 -START@4' --piano build/race-piano.png --audio-log`. The roll shows channel 2's three countdown beeps (`NR24 $86: square 2 trigger … period 1750 = A4`) and GO (`period 1899 = A5`), then the engine climbing as the car speeds up, under the race song's bass, drums and lead.
   - Crash: `--until '[wCrashes] == 1'` on `tools/lose.keys`, then `--frames 30 --audio-log` shows `NR22 $F1: square 2 envelope 15 down` and periods 600, 500, 400, 300.
   - Time up: from the lost checkpoint, `--frames 60 --audio-log` shows triggers at A4, E4, C4.
3. **The race still holds.** The win run (re-recorded by the bot, which now presses START on the title) reaches `wState == 2` at frame 2715 with 7 s left. Both write breakpoints stay silent from boot. The frame budget after the title shows `lag 0, max 66296 (94.4%), mean 83.3%`; the only lag frames are boot (0-3) and the LCD-off title-to-race switch (30-35).
4. `gbcli build` and `gbcli build --gbc` both build. On the GBC, `--model gbc` shows the colored road and car (`build/race-gbc.png`).

### Where gbcli helped

- **`--audio-log` decodes every write into notes and settings** (`period 1750 = A4 -0.6c (439.84 Hz)`, `envelope 15 down, pace 1`). I checked every effect's pitch and envelope from text, no listening needed.
- **`gbcli song FILE --piano` with no build** validated both generated songs (`instruments=7 patterns=8 orders=4`) before the build saw them.
- **The image pipeline's problem rows** named the exact rule and the offending colors and tiles when my first color art broke it (below), and the `shades=declared` summary confirmed the dmg line took effect.
- **The help's `hUGE_mute_channel` recipe** (`gbcli help music`) told me exactly how to free a channel.

### Stumbles, costliest first

1. **Color art with more than 4 colors builds only under `--gbc` (about 25 minutes, and a redesign).** I drew the road in 6 colors as color art, built with `--gbc` first, and it passed with `warnings=0`. Then the plain `gbcli build` failed: `problem limit=dmg_palette … road.png uses 6 colors; the DMG background has one palette of 4 shades … remedy: redraw it in at most 4 colors`. `gbcli help images` says color art "packs its GBC palettes and derives its DMG version". I read that as: one project builds both ways. Its DMG version is derived only in a `--gbc` build, and a `.dmg.png` override "is an error without --gbc". So a game that must build clean both ways can't use color art for a background with more than 4 colors. I switched both backgrounds to indexed art, which costs the road's GBC look (one 4-color palette for sky, grass and road together). **Ask:** let a plain build use the same derived DMG version (or the `.dmg.png`), or say plainly in the help that color art over 4 colors is `--gbc`-only.
2. **32 KB ran out under `--gbc` (about 15 minutes).** The GBC build doubles every color-art image's tiles. The link error was excellent (it listed all 9 sections pushed into bank 2, and the remedy). But moving to MBC1 isn't practical when floating `ROMX` sections (images, songs) land in whatever bank the linker picks and are read every frame. I shrank the data instead. A note in `gbcli help images` that `--gbc` color art roughly doubles image ROM would have warned me before I drew.
3. **`shared_shade` warnings only in the plain build.** The plain build gives 4 project-level `shared_shade` warnings (sprite colors share shades with the backgrounds: a red car body and a gray road are both shade 2). The `--gbc` build of the same assets says `warnings=0`. The rule is documented (color art warns only within a tile under `--gbc`), but the two builds disagreeing looks like a bug at first. These four are explained in the README (racer 4).
4. **A failed refactor command, from the worktree guard, not gbcli** (5 minutes): a multi-line `python3 -c` edit was refused and the build still passed, because the stale code assembled fine. I caught it only on rereading.

### Missing

- A way to keep a floating section (a song, an image) in bank 1, or a `--romx-bank 1` style option. That would make MBC1 practical.
- `--audio-log --channel 2` (or a filter). The full log for 6 s of music plus engine is 1,200 rows.

## Summary: building Switchback with gbcli (racer 1-4)

A pseudo-3D racer with per-line scroll writes in HBlank, sprites scaled by distance, a title, two songs, sound effects, win and lose states, DMG and GBC, in four sessions. gbcli carried the whole loop: build, run, inspect, prove. I never needed gbcli's source.

### The five costliest stumbles

1. **No PPU mode on raster writes, so "every write in HBlank" had no direct check** (about 1 hour across racer 1 and 2). `--raster` prints `into=` ticks and `raster_unsupported feature=ppu_mode_events`. I built the proof myself from conditional breakpoints on `[rSTAT]`. They are powerful, but nothing in the help suggests them for this. Because racer 1 proved it from a post-startup checkpoint, a real late write at frame 7 hid until racer 2. **Ask:** `mode=` on `raster_write`, or a recipe "did my write land in HBlank?".
2. **Color art over 4 colors builds only under `--gbc`** (about 25 minutes and an art redesign). The `--gbc` build passes clean; the plain build then fails with `dmg_palette`. The help's "derives its DMG version" reads as both ways.
3. **32 KB fills fast under `--gbc`, and MBC1 isn't practical with floating sections** (about 30 minutes across racer 1 and 3). The link error is excellent. But with no way to keep songs, images or tables in bank 1, I shrank data instead (mirrored curves, indexed art, tables to ROM0).
4. **A breakpoint condition on `[rSTAT]` can fail the run as `unsupported`** (`PPU registers are unavailable while mode-3 cycles are batched`), while `show` says it stopped at the breakpoint (about 10 minutes). It is loud, not silent, but ambiguous.
5. **Frame-budget summaries count LCD-off loads as lag** (about 10 minutes, plus `tools/budget_summary.py`). Every from-boot run says `lag=7` or `lag=10`, and its `active_max` is a loading frame. Smaller ones: `--dir` not anchoring the ROM path or `build DIR`'s session lookup, double-printed `key_unapplied` lists, the profiler naming `$0048` `VBlankVector+$8` and a WRAM routine `end_zero`.

### The three things that helped most

1. **Conditional breakpoints with `[rSTAT]`.** They found two real timing bugs that screenshots can never show, and they are the backbone of the HBlank claim.
2. **Determinism, plus held keys persisting across runs.** A 60-line Python bot drove a lap closed-loop through `gbcli run --json`, and its keys file replays the win exactly, on DMG and GBC.
3. **Diagnostics that name the fix.** The link error for a full bank (every section and the remedy), duplicate labels with both include chains, image `problem` rows with tiles and colors, and `--audio-log` decoding every sound write into notes. Each saved a trip to the .map, the PNG or the ear.
