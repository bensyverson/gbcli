# DX: Lantern Drum, the rhythm game (examples/rhythm)

Developer-experience notes from building game E with gbcli as a user (pinned binary `/Users/ben/.cache/gbcli-examples/target/release/gbcli`, gbcli 0.1.0 built from main at c38cd29, RGBDS 1.0.4 from PATH). Written blind: no other game's DX doc was read. Every command below runs from `examples/rhythm/`, with `gbcli` meaning the pinned binary.

## 2026-11-09 — Rhythm 1: timing locked to the driver (agent rhythm15)

### What I built

- `gbcli new examples/rhythm`, then replaced the starter's song with `assets/music/lantern.song`: six orders, 64 rows each, `ticks_per_row 6`, `timer off`, 2,304 driver ticks (38.6 s). Written by `tools/compose.py`, because a pattern several orders share has to be spelled out in every block that plays it (see stumbles).
- `tools/chart.py` makes the chart from the song text: every channel-1 note onset, in driver ticks, with a lane from the melody's contour. It writes `assets/music/lantern.chart` (text, beside the song) and `src/chart.asm` (the game's data); `--check` fails if either is stale.
- The game clock **is** the driver's tick count: `wNow` (src/music.asm) counts VBlanks from the start of a play; the first `PREROLL` (64) are silent while the first notes fall in, and every later one calls `hUGE_dosound` exactly once until the song's last tick. Chart times are `PREROLL + driver tick`, so judging and scrolling read the same counter the driver advances. Nothing is converted to frames, so nothing is rounded.
- **The drift risk, and how the game avoids it:** with `timer on D` the driver ticks 4096/(256−D) times a second, not a whole number of frames, and a chart rounded to frames once drifts. Lantern Drum keeps `timer off` (asserted at assembly: `ASSERT song_lantern_TIMER == 0`), so one tick is one VBlank exactly, and counts ticks rather than frames anyway. `gbcli help music` also warned that a timer tick landing just before VBlank pushes the VBlank handler's OAM DMA past VBlank, which a rhythm game's sprites can't afford. `tools/sync.py` still computes expected onset times from the exact rational tick length, so a timer-driven song would be checked correctly.
- Four lanes (LEFT, RIGHT, B, A), notes as sprites falling 2 px a tick toward a hit line at y=120, shown 56 ticks ahead. Judgment by ticks from the note: perfect within 2, good within 6, a miss once a note is 7 ticks past. Counts in `wPerfect`, `wGood`, `wMiss`; the last press's offset in `wLastDelta`.
- The name: **Lantern Drum**.

### Where gbcli helped (saved real time)

1. **`--audio-log --json` gives every sound write with `elapsed` in 2^23 Hz ticks, `addr`, `value` and decoded text.** The sync tool is 30 lines of parsing because of it: a trigger is `addr == 0xFF14 and value & 0x80`, and the note name is in the text. Exact timestamps made "no drift" a number (16 elapsed ticks over 38 s), not a judgment call.
2. **Determinism plus `--keys-file` with frame offsets from the run's start.** The open-loop key file hit every note on the first try once the start frame was known; the window sweep is nine identical runs that differ only in the key file.
3. **`gbcli help music`** answered the timing design before I wrote a line: it spells out the timer formula, that `timer off` ticks once a frame, and the timer-before-VBlank hazard. That decided `timer off`.
4. **`--until 'u16[wNow] == 0'` treating an unwritten byte as "not yet"** (documented in `gbcli help expressions`): the calibration run just works before `MusicInit` has written the clock.
5. `gbcli build` with zero config: the chart as a generated `src/chart.asm` was picked up with no build file to edit.

### Where it stumbled, by cost

1. **Shared patterns must be repeated in every pattern block** (`gbcli help music`: "A pattern several orders play is shown in every block that plays it, and every copy must read the same"). The block header is `pattern P0 P1 P2 P3`, so a song whose lead changes per order while bass, drums and pluck repeat must re-spell those three patterns in full in every block. I wrote `tools/compose.py` to generate the song instead of authoring it by hand (about 15 minutes). Expected: a per-channel pattern block (`pattern P2` alone) when a pattern is shared. The format makes the song text a build artifact rather than the source for any song with variety.
2. **`--read` takes one expression, though its usage line reads `--read EXPR…`.** `gbcli run ... --read 'u16[wNow]' '[wHead]' '[wMiss]'` failed with `gbcli: bad_request: \`gbcli run\` doesn't take \`[wHead]\``. The flag list says "repeat for more", so it means `--read A --read B`, but the `…` reads as "takes several", like `gbcli read`, which does. Cheap to work around, but every agent will hit it once. Expected: `--read A B C`, or a usage line without the ellipsis.
3. **No signed reads in expressions.** `--read 'i8[wLastDelta]'` failed with `unknown_symbol: unknown symbol "i8"`; there is `u16[...]` but no `i8`/`s8`. For a signed offset (early presses) I would read `$FC` and convert by hand. Expected: `i8[ADDR]` and `i16[ADDR]` beside `u16`.
4. **A compound shell command was refused by the worktree guard because it "names git"**: `gbcli run ... > build/sync.json; echo exit=$?; python3 -I tools/sync.py build/sync.json` was refused (probably the `.gbcli` in the path or the `;`). Not gbcli's fault (the harness), but it cost a retry; split into plain calls.
5. **Which frame a key lands on, relative to what the program reads, is not documented.** `gbcli help` says keys are "frame offsets", but not whether `A@66` is visible to a joypad read in frame 66's main loop (after VBlank) or the next. I calibrated with one press and `wLastDelta` (one extra run): `RIGHT@66` was read in frame 66. A sentence in `gbcli run --help` (keys change at the start of frame N, the VBlank boundary) would make it predictable.
6. **The audio log's `elapsed` counts from `--since`, but converting it to frames needs the frame length in 2^23 Hz ticks (140,448), which I derived from two onsets 24 frames apart.** A `frame=` (and line) field on each audio row would let a tool line onsets up with frames directly. Minor.

### Missing

- A frame number on audio-log rows (stumble 6).
- Signed expression reads (stumble 3).
- Per-channel pattern blocks in song text (stumble 1).

## 2026-11-09 — Rhythm 2: the song (agent rhythm15)

### What I built

- **Score and combo:** 300 a perfect, 100 a good, kept in BCD (`wScore`, 3 bytes, lowest first) so the HUD prints it without a division; `wCombo` and `wMaxCombo` count hits in a row.
- **Life meter:** 24 points, six cells on the HUD; a miss costs 4, a perfect gives 1 back. Empty fails the song: the music and the clock stop (`MusicStop`) and the results screen says FAILED with grade F. Six misses in a row from full fail it.
- **Results screen** (src/results.asm): counts, max combo, score and a grade, then PRESS START plays again. Grades: S is no miss and at least 90% perfect; below that by points (2 a perfect, 1 a good, out of 2 a note): A 90%, B 75%, C 60%, else D. Thresholds are assembled from `CHART_LEN`, so a new chart regrades itself.
- **HUD** on the left (score, combo, judgment word, life), lanes moved right to make room. The main loop fills a 22-byte tile buffer; the VBlank handler copies it to the map, so no VRAM write happens outside VBlank.
- **Text**: a placeholder font as pixel text, `assets/tiles/font.pixels` (42 tiles), written by `tools/font.py` from 5×7 glyphs and assigned palette `ui` in `assets/palettes.txt` so one set of tiles serves both builds; `include/game.inc` builds an RGBDS `CHARMAP` from the same character string, so `db "PERFECT"` is tiles.
- Code split by job: `main.asm` (startup, loop, VBlank, input), `play.asm` (judging, scoring, notes, HUD), `results.asm`, `text.asm`, `music.asm` (the clock). The chart's constants moved to a generated `include/chart.inc` (stumble 2).
- The song is still Rhythm 1's 38-second test song; Rhythm 3 writes the final one.

### Where gbcli helped (saved real time)

1. **`--frame-budget` named the one lag frame and its index** (`frame_cost index=2371 active_t=70208 idle_t=0 lag=1`). Index 2371 was the frame the results screen appeared, which pointed straight at `LcdOff` spinning on LY mid-frame; sleeping to VBlank with HALT first fixed it (`lag=0`). Five minutes from symptom to fix.
2. **The palette assignment error said exactly what to write.** `tiles/font.png = ui` failed with `remedy: name the image as its file is: \`tiles/font.pixels = ui\``. One edit.
3. **Build diagnostics collapse repeats and name file and line**: `src/results.asm:9: Expected constant expression: undefined symbol \`CHART_LEN\` (rgbasm, 4 times on lines 9-12)` was one row, not four.
4. **`keys_unapplied count=180 first=A@402`** on a run shorter than its key file: a warning I didn't know to ask for, which would otherwise read as "the bot stopped pressing".
5. Pixel text for the font: 42 glyphs from a short generator, previewed by the build (`build/images/tiles/font.preview.png`), with no PNG encoder to write.

### Where it stumbled, by cost

1. **My own Rhythm 1 proof broke silently when the game gained a fail state** (`sync FAILED`, `heard 6`). Not gbcli's fault, but a lesson for the plan: a check that runs the game must say what input it plays. gbcli could help by letting a run assert on a read (`--expect '[wCleared] == 1'`), which would make a recorded proof fail loudly at its own line instead of in a downstream tool.
2. **Exported constants aren't constant to rgbasm** (`Expected constant expression: undefined symbol CHART_LEN`): the grade thresholds needed the chart length at assembly time, but `src/chart.asm` only EXPORTed it. Plain RGBDS, not gbcli; the fix was a generated `include/chart.inc`. gbcli's starter could mention that shared constants belong in `include/`, not EXPORTed from a source file (about 5 minutes).
3. **`gbcli help pixels` read as if a pixel-text image is assigned by its `.png` name.** Its palettes example says `bg/town.png = forest # pixel text: bg/town.pixels`, which I read as "write .png even for pixel text". The build's error corrected it at once (helped item 2), so the cost was one build.
4. **`gbcli help images` is long (about 250 lines) for the common case** of "a font tileset that looks the same on both machines". The answer (assign a palette, so it is indexed art and one tile set serves both) is in it, but I had to read all of it to be sure color art wouldn't need its own `FontTilesGbc` load path. A three-line "which kind of art do I want" table at the top would have saved most of the read.

## 2026-11-09 — Rhythm 3: art, music and sound (agent rhythm15)

### What I built

- **The final song** (`assets/music/lantern.song`, by `tools/compose.py`): A minor, 7 ticks a row (one tick a frame, 128 BPM), ten orders: intro, verse A, verse B, chorus, A, B, bridge, chorus, final chorus, outro. 4,480 driver ticks (75 s), 165 chart notes. The composer now builds each order from a lead pattern, a chord progression (bass on the wave channel) and a drum style, and writes one pattern block per distinct combination.
- **The title loop** (`assets/music/title.song`): two slow orders, a softer lead, bass and a hat; it loops on the title screen. `MusicPlayTitle` runs it free (no clock); `MusicPlayGame` starts the game song and the clock.
- **Hit and miss sounds on channel 2 alone** (`src/sfx.asm`): a bright 2 kHz tap for a perfect, a softer 880 Hz tap for a good, a dull 131 Hz thud for a miss. Both songs leave channel 2 empty and `MusicPlay` mutes it in the driver (`hUGE_mute_channel`, as `gbcli help music` says), so an effect can never cut a note of the music, or be cut by one, whenever the press lands. The music has three voices instead of four; I judged a clean lead (the chart) worth more than a pad.
- **Art, all pixel text**: `assets/tiles/play.pixels` (blank, lane, drum hit marker, lantern note, hit burst, lattice border) and `assets/bg/title.pixels` (the name in 2x glyphs over a starry sky, a paper lantern with ribs and a glow, crossed drumsticks), both written by `tools/art.py`; the font from Rhythm 2. Every image is indexed art in palette `ui`, so one tile set serves both machines; on a GBC the program loads its own colors: a night-blue background, and a color per lane for the lanterns (amber, teal, rose, leaf) through OAM's palette bits, which the DMG ignores.
- **Screens**: a title screen (PRESS START), the play (a burst over a drum on each hit), and the results with a lattice border; START on the results goes back to the title.

### Where gbcli helped (saved real time)

1. **`--audio-summary` by writer PC answered "does anything else touch channel 2?" in one run**: 22 writes from `PlaySfx`, 2 from the driver's mute at $0421. Without it I'd have grepped a 790-row log.
2. **The image preview** (`build/images/bg/title.preview.png`, the picture and its unique tiles) showed the title at a glance and its 92 tiles, so I knew it fit in VRAM block 1 (128 tiles) before writing the loader.
3. **Indexed art plus one `ui` palette** made the GBC path trivial: one tile set, my own color tables, no `*TilesGbc` data to load.
4. **`gbcli song FILE`** as a check after each composer run (`patterns=17 orders=10`) caught nothing this time, but it is a cheap guard.

### Where it stumbled, by cost

1. **My sync tool's two silent assumptions broke on the final song, and neither was gbcli's fault**: the title loop's first channel-1 note landed in the log (166 onsets for 165 notes), and the first chart note is no longer at tick 0 (the intro is empty), which threw every residual off by 448 frames. About 10 minutes, and a lesson worth recording: anchor a sync check to the chart's own first tick, and filter the log by when the song started. A `frame=` field on audio rows (Rhythm 1, stumble 6) would have made "skip onsets before frame 63" a filter on a field instead of a multiplication.
2. **rgblink put `PlaySfx` at $0000**, in the restart-vector area before $0040 (`gbcli sym 'PlaySfx*'` showed `addr=$0000`, and the audio summary's writer PCs were $000F-$0018). I fixed it at the source: `src/main.asm` now claims $0000-$003F (`SECTION "RST vectors", ROM0[$0000]`, filled with `rst $38`), and `PlaySfx` moved to $00C8 (the PCs above are after the fix). It is RGBDS's linker, not gbcli, but the starter leaves $0000-$003F unclaimed, so a floating ROM0 section can land there, where a stray `rst $00` or a jump to 0 would run it. The starter could reserve the vector area (a `SECTION ... ROM0[$0000]` of `ds $40` minus the VBlank vector), or `gbcli build` could warn when code lands under $0040.
3. **No way to start a run's frame count, or keys, at a checkpoint and keep the key file's offsets from boot.** The sync run must replay the title and every press from boot to reach the song's end, because the key file's offsets count from the run's start. `--keys-file` with an offset (`--keys-offset -63`) or keys anchored to `--since` would let a run start `--at play` with the same file. I replayed from boot instead (each 4,700-frame run takes a few seconds, so the cost is small).

## Summary: the whole game (Rhythm 1-4)

Lantern Drum took four sessions by one agent. The risky part (judging against the driver's tick with no drift) worked on the first build, because `gbcli help music` explained the driver's tick before I wrote any code, and the audio log's exact timestamps turned "no drift" into a number. Most of the time went into the game itself and my own tools, not into gbcli.

### The five costliest stumbles

1. **Song text makes a shared pattern be spelled out in every block that plays it** (Rhythm 1, stumble 1). A song where the lead changes each order but the bass and drums repeat has to repeat them in full; I wrote `tools/compose.py` to generate the song text instead of writing it by hand, so the song text became a build product. A pattern block for one channel (`pattern P2`) would let a song be written as text. About 15 minutes, plus the composer's upkeep in every later session.
2. **Audio-log rows carry `elapsed` but no frame** (Rhythm 1 stumble 6, Rhythm 3 stumble 1). Matching onsets to the game's frames, and skipping the title loop's notes, needed the frame length in 2^23 Hz ticks (140,448), which I worked out from two onsets. A `frame=` (and `ly=`) field on each row would make audio checks line up with everything else gbcli reports by frame. About 15 minutes over two sessions.
3. **No run-level assertion for recorded proofs** (Rhythm 2, stumble 1). When the game gained a fail state, the Rhythm 1 sync proof broke silently: the run still succeeded, and only the downstream tool saw `heard 6`. `gbcli run ... --expect '[wCleared] == 1'` (exit 1 when false) would make every recorded proof fail at its own line. About 10 minutes.
4. **`--read` takes one expression though its usage line reads `--read EXPR…`**, and there are no signed reads (`i8[...]`). `gbcli run --read 'u16[wNow]' '[wHead]'` failed with `doesn't take [wHead]`; `--read 'i8[wLastDelta]'` failed with `unknown symbol "i8"`. Cheap each time, but every agent will hit the first.
5. **When a key lands, relative to the program's own joypad read, is undocumented** (Rhythm 1, stumble 5). `gbcli run --help` says keys are frame offsets but not that `A@66` is seen by a read in frame 66's main loop. One calibration run with a `wLastDelta` variable settled it; a sentence in the help would make it predictable.

### The three things that helped most

1. **`--audio-log --json` with exact 2^23 Hz timestamps, register, value and decoded text.** The whole no-drift proof is a 135-line standard-library tool over it, and the result is a hard number (the worst error over 75 s is 16 ticks, 8 CPU cycles), not a judgment. `--audio-summary` by writer PC then answered "does anything else touch the effects' channel?" in one run.

3. **`gbcli help music` and the build's diagnostics.** The help settled the timing design (the timer formula, `timer off` ticks once a frame, the timer-before-VBlank hazard, `hUGE_mute_channel` for effects); the build collapses repeated diagnostics to one row with file and line, and its asset errors name the fix (`remedy: name the image as its file is: tiles/font.pixels = ui`).
