# Design: core trait, protocol, sessions and CLI grammar

2026-11-06. Job leaf `2VP8HT` (labeled decision). **Status: approved by the user on 2026-11-06; every recommendation was accepted** (answers in [Open questions](#open-questions-for-the-user)). Nothing here is built yet.

Inputs: [the plan](2026-11-06-plan.md) (architecture and the six fidelity rules), [the backend evaluation](2026-11-06-backend-evaluation.md) (what SameBoy can and can't do, with source lines), [the DX note](2026-11-06-dx-note-existing-tools.md) (16 findings from doing a real homebrew task with PyBoy and SameBoy), and `project/agents/cli-design.md` (the house CLI rules). Section references like "DX 6" mean finding 6 of the DX note.

**The shape in one paragraph.** One binary, `gbcli`. Every CLI command is a stateless process: it opens a named session bundle, a directory under `./.gbcli/`, under a lock. It rebuilds the emulator from the session's head checkpoint (about 10 µs to restore), does one experiment, writes the new head back atomically and prints one stop record. `gbcli serve` speaks the same requests as JSON Lines over stdio for harness code. It keeps the machine in memory between requests and uses the same engine. Under both sits a `Core` trait designed for an ideal emulator core. The SameBoy backend implements it and answers *unsupported*, with a reason, for what it can't do. Every such answer is counted in a gap ledger.

## 1. Session architecture — recommendation: stateless CLI over a session bundle, plus a stdio server; no daemon

The DX note measured a fresh native process at about 25–30 ms per round trip, dominated by emulation rather than startup (DX, round-trip timings; reproduced on the main thread). So a daemon buys no latency. It buys only retained state, and that state fits in a bundle on disk.

| | Session bundle (recommended) | Daemon on a Unix socket |
|---|---|---|
| Per-command cost | Process start (~1 ms) + ROM read + state load (10.3 µs) + head write (50 KB) ≈ a few ms; emulation dominates either way | Socket round trip; emulation dominates |
| State survives | Crashes, reboots, a rebuilt `gbcli`; inspectable with `ls` and `cat` | Lost when the process dies; needs its own persistence anyway for checkpoints worth keeping |
| Lifecycle | None — no start, stop, stale socket, idle timeout or version skew between client and daemon | Start on demand, idle timeout, stale-socket cleanup, client/daemon version check, crash reporting |
| Concurrency | A lock per session; a second writer waits within its budget, then exit 3 "session busy" | Serialized in the daemon; same semantics, more code |
| Sandboxes | Writes stay in the project directory, which agent sandboxes allow | Sockets are refused in some sandboxes (Claude Code's denies local sockets outside an allowlist) |
| House rules | "Stateless commands over a stateful file beat a daemon" (cli-design ▸ State) | Must write down a trigger that measurably matters — the latency trigger was withdrawn |

**Harness clients keep their speed.** `gbcli serve` holds the engine in memory for the life of its stdin. A harness gets warm, in-process round trips, with no per-request reload, and it can still name a session to load from and save to. This is the "JSONL server" the user asked for; only its socket transport is dropped.

**This narrows a user ruling.** The plan's table says "JSONL server (stdio or Unix socket) and a CLI client". This design keeps both clients but drops the socket. **The trigger that would revive a daemon**, written down per cli-design: measured bundle overhead (load + save, excluding emulation) exceeds 10% of a typical round trip, or a feature needs live push from a running machine (a viewer window following an agent's session, remote peers). Either would also be the moment to add `serve --socket`, since the engine and protocol wouldn't change.

**Load-bearing assumption, tested first in stage 1:** save → load → run M produces the same state as running M straight through, at every instruction boundary. Stops always land between instructions (`GB_run` returns after one), and SameBoy's state covers the CPU, PPU fetcher, APU, DMA and the timers (evaluation §2). The bundle model rests on this round trip being exact; a stage-1 criterion pins it with a property test over random stop points.

### The bundle

```
.gbcli/                         found by walking up from the cwd, like .git; GBCLI_DIR overrides
  sessions/<name>/
    session.json                ROM path, symbol path, model, seed, revision counter, breakpoints, watches, taps
    head.gbck                   the current machine: a checkpoint envelope (§6)
    history/1.gbck … 8.gbck     the last 8 heads, so undo is a restore (cli-design ▸ State: undo is a verb)
    checkpoints/<name>.gbck     named checkpoints
    events.jsonl                append-only, attributed log of every request and its outcome (§10)
    lock                        flock(2) while a command runs
  cache/boot-<key>.gbck         boot-handoff checkpoints keyed by ROM, model, boot ROM and seed (§9)
  gaps.jsonl                    the gap ledger (§10)
```

- **Naming:** `--session <name>`, or `GBCLI_SESSION`. Names are `[a-z0-9-]{1,40}`. Naming one creates it. There is no `new` step, matching the house rule that naming is creating.
- **Bare invocation leaves no trace:** `gbcli run demo.gb --until …` runs ephemerally, with no bundle and nothing written except the boot cache. Without a session, a command needs a ROM argument; with one, it doesn't.
- **Listing and pruning:** `gbcli sessions` prints one row per session: name, ROM, head frame, revision, size and last use. `gbcli sessions prune --unused-for 7d` refuses without the duration. `gbcli sessions rm <name>` refuses if the session has named checkpoints, unless `--with-checkpoints`. Prune and rm read host time, which is fine: they manage files and never touch emulation.
- **Idle timeout:** not applicable; nothing stays running.
- **Where, and why not `~/.gbcli`:** sessions belong to a project (a ROM, its symbols, its checkpoints), and agent sandboxes allow writes in the project but often not in the home directory. `.gbcli/` goes in the project's `.gitignore`; `gbcli doctor` says so if it's missing.

> **Update, 2026-11-06 (stage 3, leaf IVPZ22): how the bundle store was built.** `crates/bundle` (`gbcli-bundle`) owns the `.gbcli/` layout with `GBCLI_DIR` overriding a walk up from the working directory; `crates/server` (`gbcli-server`) applies requests and speaks JSON Lines; the `gbcli` binary wires argv and stdio and has only `serve` and `version` until the CLI leaf.
>
> - **The lock is `std::fs::File::try_lock`** in a 5 ms retry loop for `LOCK_WAIT` (5 s), then `session_busy`. No libc dependency. Every session request — read or write — takes it, and the lock is per session directory.
> - **Writes are temp-file + rename**, and a head write also copies the old head to `history/s<rev>.gbck`, keeps the eight newest and drops the rest. `~N` is the history entry `rev - N`.
> - **Revision bumps only on a head change**: `run`, `step`, `restore`, `undo` and `write`. `break`, `watch`, `delete` and `checkpoint` change metadata or files but not the head. Every session response carries `rev`; a mutation that passes a stale one gets `rev_mismatch` and the last writer's name from `events.jsonl`.
> - **`serve` keeps the machine warm and reloads when the head moves.** Each request re-reads `session.json` under the lock; if its rev differs from the warm machine's, the head is loaded again. That is what makes two `serve` processes alternate safely (test: two processes, one session).
> - **The boot cache is built.** A session with no head runs the boot ROM to $0100, captures the state, and writes `cache/boot-<rom16>-<model>-<boot16>-<seed>.gbck`; later runs restore it. `--from power-on` skips it. The engine gained the fix this needed: after a candidate the engine passes over, the *next* PC begins a new core call, whose first instruction the core never checks — so the boot ROM's fall-through to $0100 was missed. The engine now checks the exec filter itself at the first PC after a step (`crates/engine/src/debug/drive.rs`; regression test `running_to_the_handoff_stops_right_after_the_boot_rom`).
> - **Measured, 2026-11-06: bundle load + save is 1.38 ms, 4.9% of a 28 ms round trip, under the 10% trigger.** `cargo run --release -p gbcli-bundle --example overhead` (200 cycles, one session, the V1 test ROM; Apple M1): meta read 32.4 µs, head read and decode 64.4 µs, head write with history rotation 1014.6 µs, meta write 264.3 µs. Core construction and state restore are not in this figure; they are per-process work a daemon would have paid too.
> - **Still not here:** ephemeral runs without a session (a CLI-leaf job; `serve` answers `no_session`), structured read forms such as `oam[0].x` (expressions only), progress events (the engine has no progress hook), and `--until`, which is leaf MBSvZS.

## 2. The `Core` trait

Designed for the ideal core, per the user's ruling. SameBoy's limits show up as `Support::No` and `Err(Unsupported)`, never as approximations. A bespoke Rust core implements the same trait, and lockstep testing steps two trait objects side by side (§2.4).

```rust
pub trait Core {
    fn info(&self) -> CoreInfo;                       // backend name, version/commit, model
    fn supports(&self, f: Feature) -> Support;        // Support::Yes | Support::No { reason: &'static str }

    // Advancing. A run always returns; nothing blocks waiting for input.
    fn run(&mut self, req: &mut RunRequest<'_>) -> Result<Stop, CoreError>;
    fn step(&mut self, unit: StepUnit) -> Result<Stop, CoreError>;   // Instruction | MCycle | Dot

    // Time. Ticks are 2^23 Hz (8.388608 MHz), the finest clock that counts both CPU speeds as integers.
    fn now(&self) -> Ticks;                           // since power-on; saved in the envelope

    // Side-effect-free inspection: never advances, syncs or perturbs anything.
    fn registers(&self) -> Registers;                 // incl. IME, halted, double-speed
    fn region(&self, r: Region) -> Result<RegionView<'_>, CoreError>;   // raw backing bytes + current bank
    fn io_register(&self, reg: IoReg) -> Result<u8, CoreError>;         // decoded value as the CPU would read it
    fn ppu(&self) -> PpuStatus;                       // LY, mode, dot (if supported), LCD on
    fn last_complete_frame(&self) -> Option<FrameRef<'_>>;              // shades 0–3 + FrameTag
    fn pixel_layers(&self) -> Result<LayerMap<'_>, CoreError>;          // which layer drew each pixel

    // The three kinds of write, never conflated (plan, fidelity rule 5).
    fn bus_write(&mut self, addr: u16, value: u8) -> Result<(), CoreError>;  // as the CPU would, with IO side effects
    fn bus_read(&mut self, addr: u16) -> Result<u8, CoreError>;              // explicit and labeled: has side effects
    fn poke(&mut self, r: Region, offset: u32, bytes: &[u8]) -> Result<(), CoreError>; // backing memory, no side effects
    fn patch_rom(&mut self, offset: u32, bytes: &[u8]) -> Result<(), CoreError>;       // file offset; recorded by the engine

    fn set_registers(&mut self, r: &Registers);
    fn set_keys(&mut self, keys: Keys);

    fn save(&self) -> Vec<u8>;                        // the core's own blob; the engine wraps it in an envelope
    fn load(&mut self, blob: &[u8]) -> Result<(), CoreError>;
}
```

- **Construction is not on the trait.** Each backend has a `new(CoreConfig)` taking the model, ROM bytes, boot ROM, RNG seed, RTC mode and rendering on or off. Determinism setup (plan, fidelity rule 3) happens in the constructor, so a core can't exist in a non-deterministic state.
- **`CoreError`** is `Unsupported { feature, reason }` | `OutOfRange { … }` | `InvalidState { … }` | `Backend { message }`. The engine turns `Unsupported` into a gap-ledger entry and a protocol error with a remedy (§5).
- **`Feature`** is a closed enum: `DotStep`, `MCycleStep`, `PixelLayers`, `SideEffectFreeIo` (decoded registers without a bus read), `ExtraOam` (FEA0–FEFF), `ApuInternals`, `WriteHookCoversDma`, and so on. `gbcli doctor --core` prints the table.

> **Update, 2026-11-06 (stage 1, leaves jQ3ATQ and m65CaC): how the built trait differs from the sketch above.** The trait lives in `crates/core` (`gbcli-core`) and the SameBoy backend in `crates/sameboy` (`gbcli-sameboy`). Changes, each made because the sketch couldn't be built as written or left a gap:
>
> - **`StopReason` holds only what a core produces:** `Budget`, `Candidate(Hit)`, `Frame`, `Step`, `Locked { opcode }` and `Stopped`. `Breakpoint { id }`, `Watch { … }`, `Predicate` and `Divergence` are decisions the engine makes on top of a candidate or a lockstep compare, so they belong to the engine's stop record, not the core (filters in the core, decisions in the engine, §2.1). A `Hit` carries the access, canonical address, bank, `old` (an `Option<u8>`: `None` when the byte can't be known without a bus read), `new`, the PC of the accessing instruction, and `vetoed`. Every `Stop` carries the next PC, its bank, `now()` and the budget used.
> - **`RunRequest` gains `veto: &AddrFilter`.** A write veto has to be decided inside SameBoy's write callback, mid-instruction, so it can't wait for the engine; matching writes are dropped and the run stops with `vetoed: true` and the attempted value. `RunRequest::new(budget)` fills in empty filters.
> - **`written(region)` is on the trait.** Never-written tracking (§9) is set by the write hook, which is in the core, so the core owns the bitmaps (CPU-written and poked, one bit per byte of WRAM, HRAM and cart RAM) and carries them in its state blob; `CoreConfig::write_tracking` turns it off. VRAM and OAM return `Unsupported(WriteHookCoversDma)`.
> - **`CoreConfig`** is shared by backends (in `gbcli-core`) and also takes `joypad_bounce`. `RtcMode` has only `Accurate`; SameBoy's host-synced mode is never offered.
> - **`Feature`** adds `PpuDot`, `ExecHookCoversInterrupts`, `Mmm01RomPatch` and `EventSinks`. On SameBoy every listed feature is `No`; event sinks aren't implemented in the backend yet (the profiler leaf adds them), so a request with a sink returns `Unsupported(EventSinks)`.
> - **The core's blob carries more than SameBoy's save state:** `now()`, the vblank count, the last complete frame, the never-written bitmaps, and SameBoy's live framebuffer. The last is needed because SameBoy doesn't save its screen: after a mid-frame load, the first frame kept the lines drawn before the load by whichever instance loaded it, and save → load → continue differed from running straight through (found by the property test). A load refuses a blob from another model, since SameBoy would silently switch models within a family.
> - **A run never stops on an execution hit before its first step**, so resuming from a breakpoint makes progress. Execution filters are checked by the run loop before each `GB_run`, so a breakpoint on an interrupt vector fires (the execution callback would miss dispatch).
> - **`set_keys` takes effect at the next emulated cycle** on SameBoy (`GB_set_key_mask` marks inputs changed; JOYP updates as emulation runs), not at once.
> - **Frames:** the core copies the frame at every `NORMAL_FRAME`, `LCD_OFF` and `ARTIFICIAL` vblank and tags it with the kind, so `shot` can refuse a non-normal frame (§9); `REPEAT` keeps the previous frame and `SKIPPED_FRAME` never fires with turbo's no-skip flag. That is the full set of SameBoy's vblank types at `ea667ad` (display.h:18–24). DMG and MGB frames are raw shades 0–3 via a sentinel palette; CGB, AGB and SGB frames are `0x00RRGGBB`.

### 2.1 Run requests: filters in the core, decisions in the engine

The per-access hooks are where speed is won or lost (DX, "what this changes": each hook costs speed directly). So the split is:

```rust
pub struct RunRequest<'a> {
    pub budget: Budget,              // Ticks | Instructions | Frames — whichever ends first; always finite
    pub exec: &'a AddrFilter,        // bank-aware bitmap: candidate breakpoints, checked BEFORE the instruction
    pub read: &'a AddrFilter,        // candidate read watches
    pub write: &'a AddrFilter,       // candidate write watches
    pub stop_at_frame: bool,         // stop after the next vblank (frame stepping)
    pub sink: Option<&'a mut dyn EventSink>,   // taps and profiler; pure data push, no core access
}
```

- **The core only filters; the engine decides.** A filter hit ends the run with `Stop::Candidate { … }` at an instruction boundary. The engine then evaluates the condition with full `&dyn Core` access over direct access (§8), and either reports the stop or resumes. This keeps conditions out of SameBoy's callbacks, where the core is mid-instruction and borrowing it again would be unsound. Hot loops whose condition is usually false pay one return per hit, which is acceptable; an unconditional breakpoint pays nothing extra.
- **Execution breakpoints stop before the instruction executes.** The run loop checks PC and bank against the filter before each `GB_run`. No byte is ever patched into game-visible memory (DX 8).
- **Watchpoints stop after the access completes.** The stop records the writer's PC, the next PC, the address, and the old and new values. Read watches use SameBoy's read callback. Known gap (evaluation §6): the write callback misses DMA destination writes, so `WriteHookCoversDma` is `No` on SameBoy, and a watch over OAM or a VRAM HDMA target warns when it's set.
- **Event sinks** receive `Event::IoWrite { reg, value, at }`, `Event::PpuMode { mode, ly, at }`, `Event::Scanline { ly, at }` and `Event::Exec { pc, bank, cycles }` (profiler only). A sink is armed only while a request uses it, so the SameBoy backend installs each callback only when it's needed.

### 2.2 Stops

```rust
pub enum StopReason {
    Budget(BudgetKind),                    // ran out: exit 3, last state attached
    Candidate(Hit),                        // engine-internal; never reaches a client
    Breakpoint { id: BreakId },
    Watch { id: WatchId, access: Access, addr: u16, old: u8, new: u8, writer_pc: u16 },
    Predicate,                             // an --until condition became true
    Frame,                                 // frame step completed
    Step(StepUnit),
    Locked { opcode: u8 },                 // illegal opcode: the CPU hangs (IE=0, halted) — evaluation §6
    Stopped,                               // STOP instruction with no wake source
    Divergence { field: String },          // lockstep only (§2.4)
}
```

The engine wraps the core's stop in the **stop record**, the one shape every run and step returns (DX 12):

```json
{"reason":"watch","pc":"$FF82","symbol":"hOAMDMA+2","bank":1,
 "writer_pc":"$FF80","addr":"$FF46","old":"$00","new":"$C0",
 "time":{"ticks":12345678,"t":6172839,"since":"boot","frame":61,"ly":144,"dot":null},
 "frame_shown":{"n":60,"vblank":"normal"},
 "budget":{"kind":"frames","limit":600,"used":31},
 "rev":"s7"}
```

- **Cycles are first-class (DX 6):** every stop record carries `ticks` (power-on, 2^23 Hz) and `t`, the CPU T-cycles since the named time base.
- **The time base is always named (DX 1)** in `since` (§9).
- **`frame_shown`** says which frame the last complete framebuffer holds and its vblank type (DX 3).
- **`dot`** is `null` when the core can't report it. On SameBoy it is always `null`, and stepping by dot is `Unsupported` (this first assumed SameBoy could report it; see the correction).

  > **Correction, 2026-11-06 (stage 1, leaf jQ3ATQ): SameBoy can't report the dot; the assumption was wrong.** SameBoy has no single dot counter. The PPU is a state machine (`display_state`) sleeping for `display_cycles`; the nearest field, `cycles_for_line`, is not a dot position. Probed at every instruction boundary over two frames of a ROM with the LCD on (a temporary shim accessor, since removed): `cycles_for_line` reads 0 through mode 2, jumps to 89 when mode 3 starts (and by batched steps, 89→136, while mode-3 cycles are batched), counts through mode 3, then is reset to 0 at the start of mode 0 for the rest of the line, and stays 0 on every line from 144 to 153 (display.c:2124–2135 resets it before the hblank sleep; the vblank loop never touches it). A dot could only be reconstructed per state from `display_state` and `display_cycles`, which would be fragile. So the SameBoy backend reports `dot: null`, and `supports(Feature::PpuDot)` is `No`.

### 2.3 Regions and direct access

`Region` is `Rom`, `Wram`, `Sram`, `Vram`, `Hram`, `Oam`, `Io`, `Ie`, `BootRom`, `BgPalette` or `ObjPalette`. Each view carries its whole backing store (all banks) and the currently mapped bank. Two traps from the evaluation become rules:

- **`Io` is raw storage, not register values** (evaluation §3: DIV, TIMA during reload, JOYP and NRxx differ). Reading a hardware register by name (`rLY`, `rDIV`) goes through `io_register`, which decodes per register. On SameBoy, registers that need a bus read to decode return `Unsupported` rather than performing one. `read io:0x04` returns the raw byte, and the output labels it raw.
- **`bus_read` exists, is labeled, and is never used by inspection.** In the CLI it is `read --bus`, and its output says "bus read: may update open bus / trigger the OAM bug". Every read verb is tested by hashing the state before and after (plan, fidelity rule 1).

> **Update, 2026-11-06 (stage 2, leaf MQqwp5): what inspection built.** The engine's inspection API is `gbcli_engine::inspect` (`crates/engine/src/inspect/`): `cpu` (registers with pairs and flags), `regions` (names per §7, banked reads by bank and offset, `region_info` with the mapped bank), `hwreg` (a table of every hardware.inc 4.6 register in FF00–FFFF plus `rIE` and `rBANK`, each with its fields and a `Source` of `Stored`, `Derived` or `WriteOnly`; a read returns the decoded value beside the raw byte), `video` (tiles, tilemaps, OAM entries with visibility and the 10-per-line limit, CGB palettes, all as data) and `apu_state`. Two additive core changes: **`Core::apu()`** returns per-channel volume, amplitude and period plus the wave table, behind the new **`Feature::ApuChannels`** (a default method returns `Unsupported`, so other backends still compile). Its `sync` field says whether the state is `Current` or `Lagging`, because SameBoy batches APU cycles (`apu.apu_cycles`) and catches up only on an APU access; a lagging state is exact for a slightly earlier moment, not an estimate. SameBoy's `GB_get_channel_edge_triggered` is left out: it clears the flag it reads. **SameBoy's `io_register` now decodes every IO address** by mirroring `read_high_memory` and `GB_apu_read` (NRxx through their read masks, wave RAM, HDMA5, BCPS/BCPD/OCPS/OCPD, OPRI, RP, PCM12/34, and 0xFF for unmapped addresses). It returns `Unsupported(SideEffectFreeIo)` only for PPU-synced registers while mode-3 cycles are batched, and for NR52, PCM12/34 and wave RAM during playback while the APU lags. Every table register is checked against a bus read on a restored copy, on DMG and CGB (`crates/engine/tests/inspect_hwreg.rs`).

### 2.4 Lockstep

`engine::lockstep` holds two `Box<dyn Core>`, steps each by `StepUnit::Instruction`, and compares a `Comparable` snapshot: registers, every region both cores expose, `now()` and the PPU status. The first difference stops with `Divergence { field }`, and the stop record names the field and both values. Lockstep can only compare what both cores support; the unsupported side of each field is listed in the report. This is how a bespoke core is checked against SameBoy (evaluation ▸ the spike), and how two SameBoy commits are checked against each other.

## 3. Budgets

Every run has a finite budget; "no answer" is exit 3 with the last stop record, never a hang (cli-design ▸ Everything terminates; DX 5).

- **Kinds:** `--frames N`, `--ticks N` (also `--t N` in CPU T-cycles at the current speed), `--instructions N`. Whichever ends first wins; the stop record says which.
- **Defaults** (an open question for the user, Q4):

  | Verb | Default budget | Wall time at ~1,400 fps |
  |---|---|---|
  | `run --until`, `run --to` | 600 frames (10 emulated s) | ≈ 0.45 s |
  | `run --frames N` | N is the budget | — |
  | `measure` | 600 frames per iteration, 100 iterations | — |
  | `step` | 1 instruction (or the given unit) | — |

- **A wall-clock guard** of 60 s backs up every request. It is a safety net, not a budget. It ends with exit 3 and `reason: budget, kind: wall`. It is the only place host time enters, and its stop record says the result is not reproducible.

  > **Correction, 2026-11-06 (stage 3, leaf IVPZ22): the reason is `wall_guard`, not `budget, kind: wall`.** A watchdog thread sets the run's interrupt flag; the server rewrites the stop reason to `StopReason::WallGuard` and answers `budget_exhausted` (exit 3) with a message saying the stop is not reproducible. The protocol's budget kinds name emulated units only, so a host-time kind did not belong among them. The budget fields also became honest: the stop record carries `budget.limits` (what was configured) and `budget.defaulted`, so a server-supplied 600-frame default is visible. A run whose budget ended it is `budget_exhausted` unless the caller named the budget explicitly, in which case reaching it is the answer.

- **Headless runs are uncapped** (DX 13): turbo on, no pacing. Pacing to real time is `--realtime`, for a future viewer.

## 4. Direct access and the three writes

| Kind | CLI flag | Protocol op | What it does | Recorded |
|---|---|---|---|---|
| Bus write | `--write rLCDC=$91` | `{"op":"write","kind":"bus",…}` | As the CPU would: DIV reset, DMA start, MBC bank switch, LCD on/off | event log |
| Poke | `--poke wSpeed=2` | `{"op":"write","kind":"poke",…}` | Backing memory; no side effects; marks the bytes written (§9) | event log |
| ROM patch | `--patch 01:4123=$00,$00` | `{"op":"write","kind":"patch",…}` | ROM backing store at bank:addr or `rom:<file offset>` | envelope patch set + event log |

- A poke to ROM is refused with the remedy "use --patch; ROM changes are recorded so checkpoints stay honest".
- A patch to the header region (`0x100–0x14F`) is refused, because SameBoy parses those bytes only at load. The remedy is to rebuild.
- MMM01 rotates its ROM in memory (evaluation §5), so patch offsets are `Unsupported` for it until someone needs it.

## 5. The JSON Lines protocol

One request per line, one final response per request, with zero or more event lines before it. The CLI builds the same request structs; both sides use **one** set of serde types in the `protocol` crate (house rule: one struct across a serialization seam).

```jsonc
// request
{"id":"7","session":"demo","as":"claude","rev":"s6","op":"run","args":{"at":"f30","poke":{"wSpeed":2},"until":"u16[wFrame] >= 60","read":["wSpriteX","oam[0]"],"shot":{"path":"a.png","scale":4}}}
// zero or more streamed events, each flushed (DX 5)
{"id":"7","event":{"kind":"progress","frame":300,"ticks":…}}
// final: success
{"id":"7","ok":true,"rev":"s7","result":{"stop":{…},"reads":{…},"shot":{…}},"warnings":[]}
// final: failure
{"id":"7","ok":false,"rev":"s6","error":{"code":"budget_exhausted","exit":3,"message":"ran 600 frames; u16[wFrame] >= 60 never held","remedy":"raise --frames, or check the predicate: u16[wFrame] is 17 at the stop","stop":{…}}}
```

- **`id`** is chosen by the client and echoed back. A missing `id` is a usage error.
- **`ok` / `error`:** `code` is a closed enum, and each code maps to exactly one house exit code. The CLI exits with it; `serve` keeps running.

  | Exit | Codes |
  |---|---|
  | 1 | `predicate_false` (assertion verbs: `check`, `measure --max`) |
  | 2 | `bad_request`, `bad_address`, `bad_expression`, `ambiguous_symbol`, `unknown_symbol`, `refused` (needs a flag) |
  | 3 | `budget_exhausted`, `rev_mismatch`, `session_busy`, `rom_changed`, `uninitialized_read` |
  | 4 | `rom_unreadable`, `checkpoint_unreadable`, `checkpoint_mismatch`, `symbols_unreadable` |
  | 5 | `unsupported`, `no_session`, `boot_rom_missing`, `toolchain_missing` |

- **Every error carries a `remedy`:** the next command, filled in with real values. A test enumerates every code and asserts a non-empty remedy for each (cli-design ▸ Errors that teach). `unknown_symbol` lists near misses; `ambiguous_symbol` lists every candidate with its bank and address.
- **Revisions:** every session response carries `rev` (`s` + the session's revision counter, which is bumped by every head change). Mutating requests may pass `rev`. A mismatch is `rev_mismatch`, exit 3, naming who changed it, from the event log. The token is per session, which is the narrowest scope that holds: all mutations go through the head.
- **Warnings** (never-written reads, frame type not normal, ROM changed but compatible) go in `warnings`. On the CLI they go to stderr as `warning: …` lines, so stdout stays parseable.
- **Batches:** `gbcli batch -F ops.jsonl` or a `{"op":"batch","ops":[…]}` request. Semantics follow cli-design ▸ Batches. It applies what can be applied, skips dependents of a failure as `cascaded`, and returns one status line per op; `--atomic` makes it all-or-nothing. An op may carry `"tag":"@a"` so later ops can refer to what it made (a checkpoint, a breakpoint id) before it exists.

> **Update, 2026-11-06 (stage 3, leaf IVPZ22): the protocol as built.** In `crates/protocol`:
>
> - `Request { id, session?, as?, rev?, op }`, with `op`/`args` as adjacent tags; `Op` covers `run`, `step`, `show`, `read`, `break`, `watch`, `delete`, `checkpoint`, `restore`, `undo`, `write`, `sessions`, `prune`, `rm`, `events` and `gaps`. `Op::name()` and `Op::mutates_head()` keep the event log and the rev check in one place.
> - A result is one `ResultBody`; only the fields its op fills are on the wire. Warnings are strings the CLI prints to stderr.
> - `read` takes §8 expressions (`u16[wFrame]`, `[$C000]`). The structured forms (`oam[0].x`) still belong to the CLI leaf.
> - A run's writes are an ordered `writes` list of `{kind, target, bytes}`; the sketch's `poke` map could not preserve the order §11 requires. `shot` waits for stage 4.
> - Error bodies carry `code`, `exit`, `message`, `remedy` and, when the machine got somewhere, `stop`. `ErrorCode` is the closed set; `ErrorCode::default_remedy` is the non-empty fallback the test enumerates. `Feature::name()` is the gap ledger's spelling.
> - `StopReason::WallGuard` and `BudgetUse::{limits, defaulted}` are the two stop-record additions.

## 6. Checkpoints

A checkpoint is an **envelope**: a small JSON header, then SameBoy's blob (plan, fidelity rule 4). One file, `.gbck`:

```
"GBCK" | u32 version | u32 header_len | header JSON (protocol::CheckpointHeader) | core blob
```

The header records:

- `core` (backend name and commit) and `model`
- `rom_sha256`, the hash of the **unpatched** ROM file, and `sym_sha256`
- `boot_rom_sha256`, `seed`, `rtc_mode` and the render config
- `ticks`, the time bases (power-on is 0; `boot` is the tick of the first FF50 write) and the frame counters
- `keys`
- `patches`, an ordered list of `{offset, bytes, before}`
- `written`, the never-written bitmap (§9), compressed as runs
- `symbols_live`, the RAM symbols and their addresses at save time, for the rebuilt-ROM check
- `created_by` and `parent`, the checkpoint or head it ran from

Hashes use SHA-256, hand-written in a small module and checked against the NIST test vectors. That's about 100 lines; a dependency isn't worth it. **Breakpoints, watches and taps are not in the checkpoint**: they belong to the session, so restoring a checkpoint never silently changes what you're watching. This narrows fidelity rule 4's "debugger configuration", deliberately. The header copies them for reference, and `restore --with-debugger` takes them.

**Verification on load, in this order.** The first failure stops the load before the core is touched.

1. **Magic and envelope version.** An unknown version gives `checkpoint_unreadable`, exit 4.
2. **Core.** A different backend is refused. A different commit of the same backend loads if the core accepts the blob, with a warning naming both commits; if the core rejects it, `checkpoint_mismatch` names both commits.
3. **Model.** The instance is built *from the envelope's model*. SameBoy would otherwise switch models silently within a family (evaluation §2). A `--model` that conflicts with the checkpoint is a usage error, exit 2. Switching families (DMG ↔ CGB) is impossible by construction.
4. **Boot ROM.** Its hash must match a boot ROM we have, either bundled or `--boot-rom`. Otherwise `boot_rom_missing`, exit 5, naming the hash.
5. **ROM.** If the hashes are equal, load. If they differ, run the rebuilt-ROM check (Q3, recommended below).
6. **Patches.** The ROM is reloaded from the file and the envelope's patch set is applied in order. Restoring a checkpoint therefore restores *exactly* its patches, including removing any made after it. The old core behavior, where patches survive a load because the load overlays the struct, never comes into play.
7. **The rest:** core blob, keys, counters, time bases, the written bitmap.

**A checkpoint loaded under a rebuilt ROM — recommendation: check by symbols, refuse when it matters, override with a flag (Q3).** RAM contents can't be "rebased": if a variable moved, the bytes at its old address are now some other variable's. So the useful rule is to detect when the old state is meaningless and refuse:

- **Refuse with `rom_changed`, exit 3** if any of these holds. The message lists each item, old → new:
  - the symbol containing PC moved;
  - a RAM symbol (WRAM, HRAM or SRAM) in `symbols_live` moved;
  - a word between SP and the top of the stack equals an old ROM-symbol address whose symbol moved (a return address that would now land mid-instruction);
  - a breakpoint's symbol moved.
- **Otherwise load with a warning** listing the ROM symbols that moved; none of them is live.
- **`--allow-rom-change`** loads regardless and records that in the event log.
- **No `.sym` on either side** means the change can't be checked, so the load is refused, with the remedy "rebuild with `-n game.sym`, or pass --allow-rom-change".

This answers DX 14 ("rebuild → restore worked, but neither tool would notice if it shouldn't have"). The DX task's v2 rebuild added one instruction, `sla b`, and moved no RAM. Whether its checkpoint loads depends on whether that instruction shifted the routine PC was in, which is exactly what the check reports. That case becomes a stage-2 test.

> **Update, 2026-11-06 (stage 2, leaf CjBWCm): how the built checkpoint differs from the text above.** In `crates/engine` (`Machine`, `Session`, `Checkpoint`, `romcheck`), with the header as `gbcli_protocol::CheckpointHeader`.
>
> - **`written` is not in the header.** The core's blob already carries the never-written bitmaps (stage-1 update under §2), so a copy would only drift. `frame` and `boot` (`{ticks, frame}` of the handoff) are; the core's blob holds the counters themselves. The render config, joypad bounce and write tracking ride in `config`.
> - **Restore and clone rebuild the core** from the unpatched ROM, apply the envelope's patches in order, then load the blob. Step 6 is exact by construction. A patch whose recorded `before` bytes differ from the ROM under it is refused (`PatchConflict`), unless `--allow-rom-change` forced a changed-ROM load, which warns instead.
> - **`symbols_live`** holds the ROM symbol containing PC, every RAM symbol, and the ROM symbols containing possible return addresses. The stack's top isn't known, so the scan runs from SP to the first RAM symbol above SP (a `wStackTop` label or the next variable), the end of SP's area, or 128 bytes, whichever is nearest, and stops at the first never-written byte. A stack word counts when it lies inside a ROM symbol; that symbol moving refuses the load (the rule above said "equals an old ROM-symbol address", which a return address almost never does). Pushed data that looks like a ROM address makes the check stricter, never looser.
> - **The "loads with a warning" case lists no moved non-live symbols.** That would need the whole old symbol table in every envelope; the warning says how many live symbols were checked instead. If agents want the list, the header can carry the old table (or the bundle store can keep old `.sym` files by hash).
> - **Breakpoint symbols** are checked from the session's breakpoints at load time (stored as `Name` or `Name+N` with the resolved address), not from the header's reference copy.
> - **`created_by` and `parent`** are recorded as the caller passes them; the engine doesn't infer a parent.

## 7. Addresses

One grammar, used by every verb and every expression:

| Form | Example | Meaning |
|---|---|---|
| CPU address | `$C0A0`, `0xC0A0` | The address as the CPU sees it, in the currently mapped bank |
| Bank-qualified | `03:4123` (RGBDS `.sym` style), `$03:$4123` | That address in that bank; required for a breakpoint or patch in a switchable region if the bank is ambiguous |
| Region + offset | `wram:0x1A0`, `sram:0x2000`, `vram:0x2000`, `oam:4`, `io:0x44`, `rom:0x14E` | An offset into the whole backing store, across banks (for example, `vram:0x2000` is VRAM bank 1); no mapping involved |
| Symbol | `wFrame`, `MainLoop`, `MainLoop+1`, `Player.update` | From the ROM's `.sym`, found next to the ROM by basename, or set with `--sym` |
| Hardware register | `rLY`, `rDMA`, `rLCDC` | Always available, with or without `.sym`, using hardware.inc names; read decoded (§2.3) |
| Structured | `oam[0]`, `oam[0].x` | OAM entries; read verbs print these as fields |

- **Symbols resolve to a bank and an address** when the command runs, and are stored that way. Errors list candidates and near misses (cli-design ▸ Address things by name).
- **Widths are explicit in expressions (DX 11).** `[x]` reads a u8, and `u16[x]`, `s8[x]` and `s16[x]` read the other widths (little-endian). When the `.sym` and `.map` show a symbol spans more than one byte, a bare `[wFrame]` warns: "reads 1 byte of a 2-byte variable; did you mean u16[wFrame]?" On read verbs, `--read wFrame:u16` is the same idea.

## 8. Conditions

A small expression language, **side-effect free by construction**. Evaluation reads only through `region` and `io_register`, so it never calls `bus_read`. It is used by `--until`, breakpoint and watch `--if`, and `check`.

- **Operands:**
  - integers in hex (`$`, `0x`), decimal or binary (`%`);
  - registers `a f b c d e h l af bc de hl sp pc`, flags `zf nf hf cf`, and `ime`;
  - memory reads `[x]`, `u16[x]` and the other widths, over any address form in §7;
  - `bank` (the current ROM bank), `frame`, `t` (CPU T-cycles since the time base) and `ly`;
  - inside a watch condition, `old` and `new`.
- **Operators:** `+ - * / % & | ^ ~ << >>`, the comparisons `== != < <= > >=`, and `&& || !`. Arithmetic is on i64 with C precedence.
- **Familiar from SameBoy's debugger:** brackets dereference and registers are bare names. Unlike SameBoy's debugger, which evaluates through `GB_read_memory` (evaluation §6), this one never touches the bus.
- **Reading never-written memory (DX 2):** an expression that reads a RAM byte the program has never written fails with `uninitialized_read`, exit 3. It names the address and symbol, and the remedy points at the time base ("wFrame is not written until frame 3 since boot; run --from boot, or pass --allow-uninit"). `--allow-uninit` turns it into a warning.
- **Parse errors show the corrected command** where one is obvious: `wFrame >= 60` gets "did you mean [wFrame] >= 60 or u16[wFrame] >= 60? A bare symbol is its address".

> **Update, 2026-11-06 (stage 2, leaf mvsVA9): as built** (`crates/engine/src/cond/`, `debug/`).
>
> - **Brackets take any expression** (`[hl]`, `[wTable + 2]`) as well as the §7 forms `03:4123` (both parts hex, prefix optional) and `wram:0x1A0` (regions `rom wram sram vram hram oam io ie boot bgpal objpal`). `u8[x]` is accepted beside `[x]`. A symbol in a switchable area (ROMX, VRAM, cart RAM, WRAMX), alone or plus or minus a constant, reads in its own bank, not the mapped one. Reads of FF00–FF7F go through `io_register` (decoded), so `[rDIV]` can be `Unsupported` on SameBoy rather than a bus read.
> - **The bare-symbol refusal applies only to RAM symbols compared directly** (`wFrame >= 60`); `pc == MainLoop` is fine.
> - **`&&` and `||` short-circuit**, so `d != 0 && x / d > 2` is safe. Division by zero, a shift outside 0–63 and an address outside $0000–$FFFF are errors, never panics.
> - **Condition symbols resolve when the run starts**, from the session's stored text; a breakpoint's location resolves when it is set. A condition that stops compiling after a rebuild fails the run naming the breakpoint.
> - **`--until` (the `Predicate` stop) is not built yet**; it needs a decision on how often a register predicate is evaluated (every instruction is slow).
> - **HALT with interrupts off** means `halted` with IE & $1F = 0. The run loop checks it, and a user break, between chunks of 4,096 instructions, so a hang is reported within 4,096 HALT ticks.
> - **Before the handoff has been seen, a `boot`-based record counts from power-on and says `since: power-on`**: the handoff's tick isn't known until it happens, so negative counts (§9) need the boot cache's checkpoint as the base. The run loop catches the handoff by keeping a write candidate on FF50 until it fires.
> - **No shadow call stack.** Tracking CALL and RET needs an execution hook on every instruction, which the SameBoy backend lacks (event sinks are unsupported). `Machine::backtrace` scans the stack instead and keeps words preceded by a CALL or RST.

## 9. Time, memory and frame rules from the DX note

- **Time bases (DX 1).** Every frame or cycle count names what it counts from:
  - `power-on` (tick 0);
  - `boot`, the handoff: the first write to FF50, which unmaps the boot ROM, with PC at $0100 on a normal boot;
  - a named checkpoint.

  **The default is `boot`.** Before handoff, counts are negative and say so. `--since <base>` changes the base on any verb.
- **Boot is cached, not skipped.** SameBoy has no boot skip; the bench's FF50 hack leaves PPU and DIV phase unlike a real boot (evaluation §1). So the first run of a ROM runs the open boot ROM (about 84 frames, ≈60 ms) and stores `cache/boot-<rom,model,boot,seed>.gbck`. Later runs start from it. `--from power-on` starts cold.
- **Never-written memory (DX 2).** The core keeps (first written as "the engine"; corrected in stage 1) one bit per byte of WRAM, HRAM and cart RAM. Each bit is set by the write hook, and by pokes, which are flagged as such in the bitmap. The bitmap is saved in the core's blob, inside the envelope. RAM randomization stays on, with an explicit, recorded seed (default 0 for ephemeral runs; sessions record theirs). VRAM and OAM are not tracked: the write hook misses DMA destinations (evaluation §6), so a bitmap there would be wrong. **The cost is measured in stage 1**: it keeps the write hook armed all the time. If it costs more than 5% of throughput, it becomes opt-in and that is recorded.

  > **Measured, 2026-11-06 (stage 1, leaf m65CaC): 2.6%, so tracking stays on by default.** Best of six interleaved runs each, `cargo run --release -p gbcli-sameboy --example bench -- tests/corpus/fetched/blargg/cpu_instrs/cpu_instrs.gb 3600 1 <mode>` (cpu_instrs, 3,600 frames after a 100-frame boot, rendering on; Apple M1, other agents' builds running, load average 3–6): `plain` (tracking off) 19.2×, `tracking` 18.7× realtime. The bitmaps live in the core, not the engine (the write hook is there), and travel in the core's state blob, which the envelope wraps; see the stage-1 update under §2. Cart RAM bits are computed for MBC1/3/5/MMM01 and no-MBC carts; MBC2, MBC7, HuC1/3, TPP1 and camera RAM writes aren't marked (their RAM paths aren't mirrored in the shim).
- **Frames and pixels (DX 3, 4).** The core copies the framebuffer at each vblank and keeps the last *complete* one with its tag: frame number since the base, and vblank type (normal, LCD-off and so on, mirroring SameBoy's vblank-type enum: normal, LCD-off, artificial, as read in stage 1; see the update under §2). `shot` reports the frame it shows, which is not the current frame. A non-normal frame (LCD off, boot) is refused with exit 1 unless `--any-frame`. `--live` gives the partial, in-progress buffer and labels it partial.
- **Streaming (DX 5).** stdout is flushed after every line. A run longer than one emulated second emits `progress` events in `serve`; on the CLI, `--progress` prints them to stderr.
- **No patched bytes (DX 8).** Breakpoints are PC checks in the run loop (§2.1). Watches use the access hooks. The only operations that change what the program sees are the three explicit writes (§4).

## 10. Determinism contract, event log and gap ledger

**Determinism.** Given the same envelope and the same request, the result is byte-identical, apart from fields documented as measurements (`elapsed_ms`). That covers:

- the stop record, every read, every image byte, and the next head state;
- RNG: SameBoy's process-wide RNG is seeded from the envelope before each `GB_init`, and is never left time-seeded;
- RTC in accurate mode, with no host time anywhere in emulation;
- joypad bounce off unless the session enables it, with the setting recorded;
- serialized instance construction, because SameBoy's RNG is global (evaluation §7). `serve` builds one core at a time.

A golden test pins this: one ROM and one request script, run twice in separate processes, must produce identical bytes. The wall-clock guard (§3) is the one documented exception, and its stop record says so.

**Event log.** `events.jsonl` in the session holds one line per request: time, `as`, the op and its args, the result code, the rev before and after, and the stop record's summary. It is append-only and rotated at 10 MB. `gbcli events` prints rows. `gbcli undo` restores the previous head from `history/`, refuses if the rev moved since the caller's read, and is itself logged.

**Gap ledger.** Every `Unsupported` an agent hits appends `{feature, reason, op, session}` to `.gbcli/gaps.jsonl`. `gbcli gaps` prints counts by feature. This is the evidence the bespoke-core decision leaf (`qfXJij`) reads.

## 11. The experiment: one round trip per question

`run` is the experiment verb (DX 15). Its steps always happen in this order, whatever order the flags are given in:

1. **Restore:** `--at <checkpoint|@tag|~N>`, or the head, or the boot cache for a bare ROM.
2. **Write:** `--patch`, `--poke` and `--write`, applied in the order given.
3. **Input:** `--keys 'A@0 -A@2 START@10'`, key events at frame offsets.
4. **Run to a stop:** `--until <expr>`, `--to <address>` (a temporary breakpoint), `--frames N`, or a session breakpoint or watch, within the budget.
5. **Measure:** `--measure <from>..<to>` reports cycles from the first arrival at `from` to the next arrival at `to`.
6. **Observe:** `--read …`, `--shot <path> [--scale N]`, `--view tiles|map|oam`.
7. **Save:** `--checkpoint <name>` saves the stop state.

On a session, the stop state becomes the new head, and the old head goes to `history/`. A session is "where you left the machine".

`measure` is the dedicated A→B verb (DX 6): `measure --from MainLoop+1 --to MainLoop --iterations 60` prints `n`, then T and M min/max/mean, then the percentage of a 70,224 T frame. It runs from the head or `--at` and leaves the head unchanged. `measure … --max 200` exits 1 if the maximum exceeds 200 T, which makes it an assertion for optimization loops. A measurement that spans a CPU speed switch is refused.

**The DX task, as one command per question.** This is the acceptance test for the grammar; the agent eval in stage 7 uses it.

| Question | Command |
|---|---|
| Is the sprite visible at frame 60? | `gbcli run demo.gb --session dx --until 'u16[wFrame] >= 60' --shot a.png --scale 4 --read oam[0]` |
| Cycles of main-loop work per frame? | `gbcli measure --session dx --from MainLoop+1 --to MainLoop --iterations 60` |
| Break when OAM DMA starts | `gbcli watch --session dx write rDMA --once` then `gbcli run --session dx` |
| What if `wSpeed` were 2? | `gbcli run --session dx --at f30 --poke wSpeed=2 --until 'u16[wFrame] >= 60' --read wSpriteX` |
| Does the rebuilt ROM behave? | `rgbasm …` then `gbcli run --session dx --at f30 --rom demo-v2.gb --until …` (§6 check runs) |

## 12. CLI grammar

**Binary name — recommendation: `gbcli` (Q1).** It is unique on `PATH`, easy to grep in transcripts and logs, and matches the repo and docs. `gb` is shorter, but generic: it collides with shell aliases and old tools, and it's hard to search for. The few tokens saved per call don't outweigh that.

**Shape:** `gbcli <verb> [target] [args] [--flags]`, everywhere. A flag means the same thing on every verb that takes it (`--session`, `--at`, `--json`, `--frames`, `--as`).

| Class | Verbs | Preconditions |
|---|---|---|
| **Read** (never changes the head) | `show` (registers + last stop), `read <addr>…`, `shot`, `view tiles\|map\|oam\|palettes`, `sym <pattern>`, `checkpoints`, `events`, `gaps`, `sessions` | A session, or a ROM plus `--at` |
| **Act** (advance or change the machine) | `run`, `step`, `measure`, `restore`, `checkpoint <name>`, `poke`, `write`, `patch`, `undo` | A session, or a ROM for an ephemeral run |
| **Configure** (session settings) | `break <addr> [--if …]`, `watch read\|write\|access <addr> [--if …] [--once]`, `delete <id>`, `tap io\|ppu\|lines` | A session |
| **Build** | `build` (runs RGBDS from `PATH`, verifies outputs exist and are non-empty — DX 10), `new` (template project) | RGBDS on `PATH`, checked against the pinned version |
| **Help** (no preconditions) | bare `gbcli` (the primer), `help <topic>`, `<verb> --help`, `recipes`, `schema`, `doctor`, `version` | None — works with no session, no ROM, no network, no TTY (DX 9) |
| **Server** | `serve` (JSONL over stdio), `batch -F <file>` | — |

- **Output:** a row per stop or item by default; `--json` gives the protocol's `result` object exactly. The bytes are the same in a pipe and in a terminal, with no color unless `--color`.
- **Writes answer with what they made:** `checkpoint f30` prints `f30 → .gbcli/sessions/dx/checkpoints/f30.gbck (frame 31 since boot, rev s4)`; `break MainLoop` prints its id.
- **Bodies come from files:** batch ops via `-F`, key scripts via `--keys-file`. No inline free text needs quoting beyond expressions.
- **The primer** (bare `gbcli`) gives what it is, the verbs by class, the first command to run (`gbcli run <rom> --frames 120 --shot first.png`), and where help lives. It must fit in 40 lines; the agent eval sizes the rest.
- **Help topics:** `addresses`, `expressions`, `time` (time bases), `checkpoints`, `writes` (the three kinds), `budgets`, `exit-codes`, `hardware` (a minimal DMG primer that links out to Pan Docs), and `optimize` (the measure → patch → measure loop).
- **Recipes:** goal → command routing, for example "how many cycles does X take → `measure`", "why is the screen blank → `shot --any-frame` then `read rLCDC`", "find who writes a variable → `watch write`".
- **`doctor`** checks RGBDS and its version, boot ROMs, `.gbcli` in `.gitignore`, the core's support table, and the sandbox's writability.
- **The argument parser is a dependency question (Q5):** a small hand-written parser over `std::env::args`, or a crate.
