# Architecture

Which crate owns what. gbcli is a Rust workspace: library crates hold every decision, `gbcli-server` and `gbcli-cli` are thin adapters over them, and the `gbcli` binary only wires argv, the environment and stdio into `gbcli-cli`. The approved design behind this is [project/2026-11-06-design.md](../project/2026-11-06-design.md).

Add a crate or a major capability here when you build it; keep the head of `AGENTS.md` free of feature lists.

## The emulator

- **`crates/core` (`gbcli-core`)**: the `Core` trait, our own seam over any emulator backend, and its types (`CoreConfig`, cart clocks, flash notes).
- **`crates/sameboy-sys`**: vendored SameBoy, built by the `cc` crate, with hand-written FFI and the small C accessors in `shim/`. The vendored commit, compile flags and patches: [project/2026-11-06-sameboy-vendoring.md](../project/2026-11-06-sameboy-vendoring.md).
- **`crates/sameboy` (`gbcli-sameboy`)**: the SameBoy backend implementing `Core`: bank-aware filters, never-written tracking, the checkpoint blob, and a flash chip on flash-save carts.
- **`crates/flash` (`gbcli-flash`)**: an AMD/JEDEC flash-chip model for flash-save carts such as GB Studio's batteryless saves, parameterized by board (unlock addresses, D0/D1 swap, sector map, /WE pin, chip size, busy times) with named profiles from FlashGBX's database; commands that miss the board become `FlashNote`s, and mask-ROM programs that send flash commands get a hint. A session takes a board with `--flash BOARD` (`gbcli help flash`; [project/2026-11-07-flash-model.md](../project/2026-11-07-flash-model.md)).

## The engine and the session

- **`crates/engine` (`gbcli-engine`)**: inspection, the disassembler and `gbcli opcode`'s lookup (`disasm::lookup`, checked against rgbasm by a seeded differential test), sessions, checkpoints, the debugger (whenever the session's breakpoints and watches meet a machine, each set by a symbol moves to where the `.sym` on disk puts it, so they follow a rebuild, and is disarmed (`Arming::Disarmed`, kept but stopping nothing) while that `.sym` lacks its symbol: `Machine::attach_debugger`), a run's key timeline (`KeyTimeline`: offsets from the run's start, or from a time base for `run --keys-since`, dropping the events before the run's start), the cycle profiler (`measure`: cycles between two addresses, on a copy of the head, `--at`, or `--from boot|power-on` (wire `start`: `from` is the span's first address), under a run's key timeline when given one; cycles per routine, named by the `.sym` label at the entry or the hardware vector there (`STAT_vector`; `profile::names::name_at` names stop rows too, and the header `$0100-$014F` as `Header`), with the HALT share of each routine's exclusive cycles (`idle_t`), and the per-frame budget, which counts a frame the LCD was off for apart from lag and numbers each frame as a stop record counts frames) and the A/B equivalence check (`equiv::compare`: two builds under one key timeline, the first frame whose pixels, chosen RAM or sound-register writes differ, naming a RAM byte a side has never written, so its power-on value is random, and how much sooner one side's divergent frame ended (`FrameOffset`), counted from each side's start; the screen compare can be off (`ScreenCompare::Off`) so a RAM compare stands alone for builds whose timing differs, and a check with nothing left to compare is refused). Run's `--measure`, `--profile`, `--frame-budget` and `--raster` (IO-register writes by line, each with the PPU mode it landed in, which `crates/sameboy` reads from SameBoy's display state without running it, as it does `Core::ppu().mode`; both are unknown, never wrong, in the one window that state can't answer) come from here. `inspect::video` decodes tiles, maps, OAM (with the 10-per-line drops) and the palettes (`palettes`: BGP/OBP0/OBP1, and palette RAM on a CGB) for `view` and `run --oam-log`. `Symbols::containing` picks, among labels at one address, any but an end marker (`TilesEnd`, `end_zero`), since the `.sym` alone can't say which section a label ends; `Symbols::label_any_bank` names a PC recorded without its bank (an audio writer's) only where one bank can hold it, and `gbcli_audio::name_writers` skips a writer that wrote from the boot ROM (`ApuWrite::boot_rom`). `cond::BlockStart` reads a block of bytes for `view memory`, each as `[ADDR]` reads it (the same place grammar, bank rules and never-written check, one warning for a block's never-written bytes); a block from a bank or region that would run past its area's end is refused (`EvalError::BlockPastArea`). `cart::cgb_flag` reads the header's CGB flag ($0143) for `show` and `sessions`.
- **`crates/protocol` (`gbcli-protocol`)**: the wire types every crate shares: requests and responses, the checkpoint header and stop record, the build and image results, and the named palettes with their one rule set (`NamedPalettes::check`, which the file parser and deserialization both apply). A type crossing the JSONL seam is defined once, here. So is `PROTOCOL_VERSION`, which the `version` op reports and which goes up on any breaking wire change.
- **`crates/bundle` (`gbcli-bundle`)**: the session bundle store (no daemon).
- **`crates/corpus` (`gbcli-corpus`)**: the test-ROM runner and the SameBoy baseline ([project/2026-11-06-sameboy-baseline.md](../project/2026-11-06-sameboy-baseline.md)).

## Views

- **`crates/view` (`gbcli-view`)**: image views as deterministic PNG pinned by goldens: labeled frames, scales and crops, filmstrips, frame diffs, tileset, tilemap and OAM.
- **`crates/audio` (`gbcli-audio`)**: the sound-register write log decoded into notes and settings, WAV export (mixed and per channel), piano roll and spectrograms, pinned by goldens; wired into `run` as `--audio-log` (each write with the frame and line it fell on, from the core's `ApuWrite`), `--audio-summary` (writes by register and writer PC), `--audio-channel N` (the log and summary narrowed to channels), `--wav PATH [--channels each]`, `--piano PATH` and `--spectrogram PATH`.

## The build loop and assets

- **`crates/build` (`gbcli-build`)**: the RGBDS loop.
  - **Toolchain and build:** RGBDS from `PATH` checked against the 1.0.4 pin; a build by convention (to `build/NAME.gb`, or `build/gbc/NAME.gbc` under `--gbc`, a folder of its own so each ROM keeps its own `.sym` and `.map`: `project/layout.rs`) with every diagnostic as a file, line and message (a message repeated line after line is one, with its last line and count; `diagnostics/hints.rs` gives a remedy for messages that don't say their fix); `doctor`'s checks.
  - **The starter:** `new` scaffolds a project (vendored hardware.inc, hUGEDriver and a player for `assets/music/theme.song`, and a text renderer, `src/text.asm`, with a font drawn for gbcli, `assets/fonts/main.yaff`, drawing one line into a 20-tile line buffer, tiles 236-255) with its own `.gbcli/`, so sessions run inside it stay there even under another project's. Its `main.asm` claims the restart vectors ($0000-$003F, 64 bytes of `rst $38`), so rgblink can't float a section into them. `build --gbc` defines `GBCLI_GBC` for every source, so the starter's color path is assembled only then, and it decides at run time from the boot's A and its own header.
  - **Music:** songs under `assets/music` become hUGEDriver data by convention.
  - **Images:** PNGs (or pixel text, `.pixels`, read through `gbcli-pixels` and written to a transient PNG for rgbgfx; a bad one is a `pixels_text` problem with line and column, and a hardware problem on one gives the line that drew the tile; while `assets/palettes.txt` doesn't read, a palette reference that can't resolve is not reported, only the file's own error) in `assets/bg/`, `assets/sprites/` and `assets/tiles/` (tilesets: a background's tiles with no map) are checked against the hardware's limits (structured problems with remedies), converted by rgbgfx, previewed, and exposed through a generated `images.inc` and `images.asm` (`gbcli help images`). Sheets are 8x16 objects, or 8x8 when a frame size is a multiple of 8 high but not 16, unless the project sets one size for every sheet (the `objects` line of `assets/palettes.txt`, or a manifest's `objects`) (`images/sheet.rs`). `images/input.rs` gathers a project's images (or a manifest's, and where its palettes came from, which remedies name) and `images/pipeline.rs` converts them, for `build` and for `assets` (`src/assets.rs`), which converts without rgbasm or rgblink, writes nothing unless asked, and returns the results a build records.
  - **Fonts:** every `assets/fonts/NAME.yaff` (or a manifest's `fonts`) is read through `gbcli-font` (`images/fonts.rs`), never deduplicated, in file order. A build emits each font of at most 254 glyphs (or its character list's, `NAME.charlist`, past that; else `font_glyphs`) into the same `images.asm`/`images.inc` as `<Name>FontGlyphs`, `<Name>FontWidths`, constants and a `<NAME>_FONT_CHARMAP name, base` macro (`images/emit/font.rs`); `assets` returns the glyphs a request's `glyphs` names, with no cap. Both report `FontAsset` in `ImagesMade.fonts` (`gbcli_protocol::font`, the seam LoadHigh reads). `src/font.rs` is the `font` op (`gbcli font FILE --sample/--preview/--fit`). A letter a request or a character list asks for that the font doesn't draw is composed from its drawn base and mark (`gbcli_font::compose`), after the drawn glyphs, `origin: composed`, with a mark on its base's ink a warning in `ImagesMade.font_overlaps`. `src/font_author/` is the authoring ops (`gbcli font edit/save/import/export/new/diff`): it reads and writes the files around `gbcli-font`'s conversions and keeps the working copy in the project's `build/font-edit/` (`copies.rs`), with `NAME.base` recording the font it was made from, which `save` checks before writing (`base.rs`, `save.rs`: the decisions take data); export, guide sheets and diff PNGs never write over a `.yaff` or into that folder (`io.rs`); a build (and `assets`) refuses while a project font's copy is newer than it (`images/fonts.rs`, `find`).
  - **GBC images** (Stage 10, [project/2026-11-07-gbc-images-plan.md](../project/2026-11-07-gbc-images-plan.md)): `build --gbc` writes a dual-mode header; every build, plain or `--gbc`, derives each color image's DMG version (`images/derive.rs`; a `name.dmg.png` overrides it); a session made with `--model gbc` runs it as a GBC. `images/pack.rs` packs color art into GBC palettes deterministically; `images/gbc.rs` converts color art's GBC tiles behind the one tilemap or frame list both machines share (tiles deduplicated on the pair of versions; `images/output.rs` converts each checked image). `images/indexed.rs` gives indexed art (an image `assets/palettes.txt` assigns a palette) its GBC result: its DMG tiles, and a slot in each tile map entry (a sheet's slot holds its palette reordered by its OBP, so slots are keyed by palette and OBP). `images/emit/gbc.rs` writes the labels (`*TilesGbc`, `*Attrmap`, `*Palettes`, `ObjPalettesGbc`, every named palette as `Palette<Name>`, and each indexed sheet's swap copies `<Sheet>Palette<Name>`), and `images/preview.rs` draws a `.gbc.preview.png` in screenshot colors.
- **`crates/pixels` (`gbcli-pixels`)**: pixel text, images as text an agent can write and read (`.pixels`, `format gbcli-pixels 1`; [project/2026-11-08-pixel-text-design.md](../project/2026-11-08-pixel-text-design.md)): the parser (blocks painted in file order, parse errors located to line and column), the canonical writer (rows by frame or 8-row band, or `--tiles`: tiles keyed in hex by first use and a map), PNG decode and encode, the legend a PNG's colors get (`.` clear, then lightest first) and a 4x preview with an 8x8 grid. `PALETTE N` and `dmg N` resolve through a `Palettes` the caller reads; `gbcli-build`'s `pixels` (the `pixels` op and `gbcli pixels`, `gbcli help pixels`) reads them from the project's `assets/palettes.txt` or `--palettes`.
- **`crates/font` (`gbcli-font`)**: pixel fonts ([project/2026-11-09-pixel-fonts-design.md](../project/2026-11-09-pixel-fonts-design.md), Ben's decisions): gbcli's own strict-subset YAFF reader and writer (`yaff::syntax` reads all of YAFF 1.0, so a file outside the subset is refused for what it is at its line; `yaff::strict` holds it to gbcli's rules; the writer is canonical), keys (`Key`: a character, a code point or a name; `<name>` in a charmap), the mark table (`marks`, generated from Unicode's data by `scripts/fonts/gen_marks.py`, so a decomposed key is refused naming its precomposed letter with no normalization dependency), the layout rules (`layout::RULES`, which `gbcli help fonts` prints verbatim, and `set`/`draw`, the reference `gbcli font --sample` uses) and previews. The authoring conversions are here too, data in and data out (no files, so they build for a web target): the PNG working copy's grid and its `.chars` sidecar both ways, with guides and every disagreement a `Problem` naming its cell (`grid`, `chars`), BDF out and in, trimmed glyphs placed by bounding box and ascent (`bdf`), composition (`compose`), a glyph-by-glyph diff and its picture (`diff`), the named character sets (`sets`) and a 3x5 label font for the guide sheet and the diff (`labels`). Tested against two of monobit's published samples, vendored with their licenses in `crates/font/data/monobit/` (`SOURCE`).
- **`crates/music` (`gbcli-music`)**: hUGETracker songs: `.uge` v0-v6 read and v6 written, a canonical tracker-grid text form both ways with parse errors located to line and column (on input a block may name fewer than four patterns, `=` for one another block shows, so a shared pattern is written once: `text/grid.rs`), a piano roll drawn from a song file, and the song to RGBDS `.asm` emitter, a port of hUGETracker's export (`gbcli song`, `gbcli help music`).

## Adapters

- **`crates/server` (`gbcli-server`)**: request handling over the library crates, screenshots, VRAM, OAM, palette and memory views (`view memory`, `handle/memory.rs`), the per-frame OAM log (`run --oam-log`), key input on runs, `run --expect` (conditions at the stop beside the reads; one false fails the run with `predicate_false`, the run saved and its result on the error: `handle/run/expect.rs`), and the JSONL stdio server (`gbcli serve`). A request's relative file paths (shots, PNGs, WAVs, `.sav`s, a build's) start at its `Host`'s working directory: the CLI's, which `--dir` moves.
- **`crates/cli` (`gbcli-cli`)**: argv to protocol requests, answered in-process by the server's handler; rows or `--json` (the serve response line), where any per-frame or per-event list prints a summary or at most 20 rows in text and every item in `--json` (`render::row::capped`; guarded by `render/bounded_tests.rs`; the summaries' groupings, such as `FrameBudgetMade::lag_runs`, are methods on the protocol types; design §12, "bounded rows"); the primer, `--help`, help topics, recipes and the schema. Every server op is a verb; `gbcli --help` lists them, and `crates/cli/src/verbs/` holds the table.
- **`crates/gbcli`**: the binary, and the CLI's golden transcripts (`tests/cli/`).
