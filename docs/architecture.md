# Architecture

Which crate owns what. gbcli is a Rust workspace: library crates hold every decision, `gbcli-server` and `gbcli-cli` are thin adapters over them, and the `gbcli` binary only wires argv, the environment and stdio into `gbcli-cli`.
The approved design behind this is [project/2026-11-06-design.md](../project/2026-11-06-design.md).

Add a crate or a major capability here when you build it; keep the head of `AGENTS.md` free of feature lists.
Write one sentence per line (continuation lines indented under their bullet), so agents that document the same crate in parallel touch different lines and merge.

## The emulator

- **`crates/core` (`gbcli-core`)**: the `Core` trait, our own seam over any emulator backend, and its types (`CoreConfig`, cart clocks, flash notes).
- **`crates/sameboy-sys`**: vendored SameBoy, built by the `cc` crate, with hand-written FFI and the small C accessors in `shim/`.
  The vendored commit, compile flags and patches: [project/2026-11-06-sameboy-vendoring.md](../project/2026-11-06-sameboy-vendoring.md).
- **`crates/sameboy` (`gbcli-sameboy`)**: the SameBoy backend implementing `Core`: bank-aware filters, never-written tracking, the checkpoint blob, a flash chip on flash-save carts, and the logs behind a run's hardware warnings (the LCD turned off outside VBlank; VRAM and OAM writes the PPU ignored, counted exactly through a SameBoy patch), whose wording the engine owns.
- **`crates/flash` (`gbcli-flash`)**: an AMD/JEDEC flash-chip model for flash-save carts such as GB Studio's batteryless saves, parameterized by board (unlock addresses, D0/D1 swap, sector map, /WE pin, chip size, busy times) with named profiles from FlashGBX's database; commands that miss the board become `FlashNote`s, and mask-ROM programs that send flash commands get a hint.
  A session takes a board with `--flash BOARD` (`gbcli help flash`; [project/2026-11-07-flash-model.md](../project/2026-11-07-flash-model.md)).

## The engine and the session

- **`crates/engine` (`gbcli-engine`)**: inspection, sessions and checkpoints, and:
  - **The disassembler** and `gbcli opcode`'s lookup (`disasm::lookup`, checked against rgbasm by a seeded differential test).
  - **The debugger:** whenever the session's breakpoints and watches meet a machine, each set by a symbol moves to where the `.sym` on disk puts it, so they follow a rebuild, and is disarmed (`Arming::Disarmed`, kept but stopping nothing) while that `.sym` lacks its symbol (`Machine::attach_debugger`).
    Ids are never reused, counted by `DebuggerConfig.next_id` in the session.
  - **A run's key timeline** (`KeyTimeline`): offsets from the run's start, or from a time base for `run --keys-since`, dropping the events before the run's start.
  - **The cycle profiler:** `measure` counts cycles between two addresses, on a copy of the head, `--at`, or `--from boot|power-on` (wire `start`: `from` is the span's first address), under a run's key timeline when given one.
    Cycles per routine are named by the `.sym` label at the entry or the hardware vector there (`STAT_vector`; an RST slot's first byte, where `rst` or an $FF byte run as code enters, is the slot's (`RST_38`), and past it a game label running over the slot names the code; `profile::names::name_at` names stop rows too, and the header `$0100-$014F` as `Header`), with the HALT share of each routine's exclusive cycles (`idle_t`).
    The per-frame budget counts a frame the LCD was off for apart from lag, and numbers each frame as a stop record counts frames. A frame that never halted is LCD-off too when the next frame turns the LCD off before halting (a screen change's wait for VBlank), so `FrameSplit` returns each frame one cut late and `finish` settles the last by what the run saw of the next (the machine keeps the first LCD-off of the latest frame, `Machine::first_lcd_off_in`).
  - **The A/B equivalence check** (`equiv::compare`): two builds under one key timeline, the first frame whose pixels, chosen RAM or sound-register writes differ, naming a RAM byte a side has never written (so its power-on value is random), and how much sooner one side's divergent frame ended (`FrameOffset`), counted from each side's start.
    The screen compare can be off (`ScreenCompare::Off`) so a RAM compare stands alone for builds whose timing differs, and a check with nothing left to compare is refused.
  Run's `--measure`, `--profile`, `--frame-budget` and `--raster` (IO-register writes by line, each with the PPU mode it landed in, which `crates/sameboy` reads from SameBoy's display state without running it, as it does `Core::ppu().mode`; both are unknown, never wrong, in the one window that state can't answer, where `Core::ppu().mode` still says `PpuModeKnown::HBlankOrDrawing` and a condition answers `mode == 1` from it) come from here.
  `inspect::video` decodes tiles, maps, OAM (with the 10-per-line drops) and the palettes (`palettes`: BGP/OBP0/OBP1, and palette RAM on a CGB) for `view` and `run --oam-log`.
  `Symbols::containing` picks, among labels at one address, any but an end marker (`TilesEnd`, `end_zero`), since the `.sym` alone can't say which section a label ends;
  `Symbols::label_any_bank` names a PC recorded without its bank (an audio writer's) only where one bank can hold it, and `gbcli_audio::name_writers` skips a writer that wrote from the boot ROM (`ApuWrite::boot_rom`).
  `cond::BlockStart` reads a block of bytes for `view memory`, each as `[ADDR]` reads it (the same place grammar, bank rules and never-written check, one warning for a block's never-written bytes); a block from a bank or region that would run past its area's end is refused (`EvalError::BlockPastArea`).
  `cart::cgb_flag` reads the header's CGB flag ($0143) for `show` and `sessions`.
- **`crates/protocol` (`gbcli-protocol`)**: the wire types every crate shares: requests and responses, the checkpoint header and stop record, the build and image results, and the named palettes with their one rule set (`NamedPalettes::check`, which the file parser and deserialization both apply).
  A type crossing the JSONL seam is defined once, here.
  `RasterMade::drawn` is the scroll each visible line began drawing with, a frame at a time: `Event::LineScroll`, sampled at `mode_3_start` by `patches/raster-line-scroll.patch`, because a write's reported mode can't place one in the dots between STAT reading 3 and the first fetch: a write in those dots is in the line's entry, and one after them stays in the trace and first appears in the next line's entry. `RasterMade.lines` counts a drawn line the core gave no start for, such as line 0 after the LCD comes on.
  `RasterMade::writers` orders the raster writers riskiest first (writes in drawing, then unknown mode, then OAM scan; the safe ones in first-write order), so a capped text view hides the safest.
  So is `PROTOCOL_VERSION`, which the `version` op reports and which goes up on any breaking wire change.
  A request may carry `wall_guard_s` (1-3600, `WallGuardSeconds`), which the server arms its watchdog with instead of its 60 s default; a request the guard ends answers `wall_guard` (exit 3).
  It also holds gbcli's one mark table (`marks`: every precomposed Latin-1 and Latin Extended-A letter, and every kana voiced by U+3099 or U+309A, as a base and one combining mark, with `compose`, `decompose`, `singleton` (the characters NFC replaces by a table letter, a row's base or a mark: U+212A KELVIN SIGN is K) and `is_combining_mark`), generated from Unicode's data by `scripts/fonts/gen_marks.py`; it is here, as data with no I/O, so that gbcli-font and consumers such as LoadHigh (which composes its string literals with it) read one table with no normalization dependency.
  It composes a base followed by one mark from its scope, left to right, after mapping the singletons, with no canonical reordering (it holds no combining classes): NFC for a base and mark pair the table holds, not for every string (NFC also composes pairs whose letter lies outside the table's scope, A and U+030C to U+01CD, and maps singletons the table doesn't hold, such as U+2126 OHM SIGN).
- **`crates/bundle` (`gbcli-bundle`)**: the session bundle store (no daemon).
  - **The store trait:** every bundle decision (`Bundle`, session creation, the history ring, checkpoints, pruning, events, the gap ledger, listing, the ROM stamp) is written against `ProjectStore` (`project_store.rs`), a key-and-blob store with directories: `get`, `get_range`, `size`, `change_token`, `put`, `put_all`, `append`, `remove`, `remove_tree`, `rename`, `list`, `kind`, `make_dir(s)`, `lock`, `touch`, `last_used`, `new_incarnation`, `key_of`, `canonical_key` and `locate`. Errors are `io::Error`s, a missing key being `NotFound`, so messages read as they did over files. `put` is an atomic replace by contract (a reader sees the old blob or the new one), and no write creates its key's parent, so a write under a removed session fails instead of resurrecting it. `Bundle` holds the store as `Arc<dyn ProjectStore>`, so a backing can live outside the crate, and a `Clock` (`Arc<dyn Clock>`) its decisions read now from: the logs' `at`, a listing's fallback `last_used`, pruning's cut. No decision module opens a path or reads the clock; incarnations come from the store, not a process id.
  - **The filesystem backing:** `FileStore` (`file_store/`, with `io.rs`) is the only place the crate touches files or the host clock (`SystemClock`). A key is a path under the project (or, absolute, outside it); `put` is a temp file and a rename, `lock` is `flock` with its wait, an incarnation is a random value from the standard library's hash keys and a counter, `key_of` (the key a read or write goes through) resolves a path's directory as the project's own path is resolved but keeps its name, so a symbolic link is followed at each read and a write replaces the link itself, and `canonical_key` (which file a session was made from, and whether two paths name one file) resolves every link. A change token is size, mtime, device and inode, and unsettled while the file is under 2 s old. Finding the project (walking up for `.gbcli/`, `GBCLI_DIR`) is here too, as `Bundle::open*` (`file_store/open.rs`).
  - **The memory backing:** `MemoryStore` (`memory_store.rs`) is a map from key to blob or directory, for a caller with no filesystem. `MemoryStore::new(root, clock)` names the project's path (absolute, or it is refused with `RelativeRoot`; nothing need exist there) and the clock that dates its writes. Its caller seeds it with the ROM and `.sym` under project keys (`put`) and makes the bundle's directory, then builds `Bundle::new(store, Key::new(".gbcli"), clock)`; nothing persists it. Directories are tracked explicitly, the project and `/` among them, each with a last use; `lock` succeeds or answers `Busy` at once (one owner, no waiting thread), and a new lock is an empty blob with no use recorded that dates its directory; a write records its time on the blob and its directory, for the last-use fallbacks; a change token is the write counter at the blob's last write, always settled; an incarnation is a counter (a backing that persisted the store would have to persist it too). The two backings answer the edge cases alike (a blob call on a directory is `IsADirectory`, `make_dirs` through a blob `NotADirectory`, `make_dir` over a blob `AlreadyExists`), held to it step by step by `store_parity_tests.rs`. `key_of` resolves `.` and `..` lexically and strips `root`, so a path under `root` is a project key and any other is a key outside the project (held like any other once its directory is made); with no aliases, `canonical_key` is `key_of`. A key with `.`, `..` or an empty part is refused (`InvalidInput`), since `Key::new` normalizes nothing and `a/../b` would be another blob than `b`. The coupling to watch: the server resolves a request's paths against its `Host`'s working directory before the store sees them, so that directory must sit under `root` (tested in `crates/server/src/handle/memory_store_tests.rs`).
  - **Keys:** the store is rooted at the project, not the bundle. The bundle's keys start with its directory's name (`.gbcli/`, or under `GBCLI_DIR=/work/state` the project is `/work` and they start `state/`): `sessions/<name>/{session.json,events.jsonl,events.1.jsonl,history/s<rev>.gbck,checkpoints/<name>.gbck}`, `locks/<name>.lock`, `removed/`, `cache/boot-<key>.gbck` and `gaps.jsonl`. The ROM, its `.sym`, battery saves and the images and WAVs a request writes are keys like any other: `session.json`'s `rom` and `sym` are the keys themselves (relative to the project when inside it, else absolute), so `SessionFile` and `RomSource` keep their shapes and a memory caller puts the ROM (and `.sym`) into its store when it builds it. The verbs that read or write a request's own files (shot, filmstrip, audio, view, memory dumps, and battery import and export with the flash image) read and write them through `Bundle::{read_file,write_file,write_files,is_dir,exists}` (`crates/server/src/handle/files.rs`), resolving them against the host's working directory first. Known debt: build, font, pixels and assets still read and write host paths directly.
  - **Last use:** `touch(lock key, now)` records a use when a request takes a session's lock, and `last_used` reads it back; a lock no use was recorded on reads 0. The file backing keeps it as the lock file's mtime (a new lock file is dated to the epoch), and a listing or prune falls back to `session.json`'s and then the directory's `last_used`, which the file backing answers from their mtimes.
  - **The ROM stamp** (`stamp.rs`) keeps a warm machine only while the ROM and `.sym` hold the bytes it was built from. A check asks the store for each file's `ChangeToken` (opaque to the stamp, which reads no clock and no file times) and is that alone when the token vouches for the stamped one; otherwise it reads and hashes the file and compares the SHA-256 with the built machine's (`FilesStamp::built`) or the `.sym`'s from the stamp, so a touch that keeps the bytes keeps the machine. Each check resolves the session's own path, so a retargeted link is seen.
- **`crates/corpus` (`gbcli-corpus`)**: the test-ROM runner and the SameBoy baseline ([project/2026-11-06-sameboy-baseline.md](../project/2026-11-06-sameboy-baseline.md)).

## Views

- **`crates/view` (`gbcli-view`)**: image views as deterministic PNG pinned by goldens: labeled frames, scales and crops, filmstrips, frame diffs, tileset, tilemap and OAM; and a frame's pixels as data with their fingerprint (`screen.rs`: `shot`'s `pixels=` and, asked for with `ShotArgs::screen` (`--screen-rows`, which the CLI refuses without `--json`), its `screen` rows: shades on a DMG, the core's colors elsewhere).
- **`crates/audio` (`gbcli-audio`)**: the sound-register write log decoded into notes and settings, WAV export (mixed and per channel), piano roll and spectrograms, pinned by goldens; wired into `run` as `--audio-log` (each write with the frame and line it fell on, from the core's `ApuWrite`), `--audio-summary` (writes by register and writer PC, and each take's loudness: `gbcli_audio::loudness`, the median DC-removed RMS of its 1/64 s windows, leaving out the first window and those within 128 samples of a DAC switch the write log names, over the same muted replays as per-channel WAVs; `Level` on the wire says a figure, `silent` (windows measured, none sounding) or `unmeasured` (no window left, as in a 1-frame run); none on the SGB, which can't capture samples), `--audio-channel N` (the log and summary narrowed to channels), `--wav PATH [--channels each]`, `--piano PATH` and `--spectrogram PATH`.

## The build loop and assets

- **`crates/build` (`gbcli-build`)**: the RGBDS loop.
  - **Toolchain and build:** RGBDS from `PATH` checked against the 1.0.4 pin; a build by convention (to `build/NAME.gb`, or `build/gbc/NAME.gbc` under `--gbc`, a folder of its own so each ROM keeps its own `.sym` and `.map`: `project/layout.rs`); a header with no MBC that rgblink spills past bank 1, can't fit in bank 0, or refuses for a section bigger than a 16 KB bank is linked again as one 32 KB bank (`rgblink -t`, `project/banks.rs`) with a warning row, so only such a build pays a second link.
    When that link fails too: after a spill past bank 1 the header is known, and the report names the section the one-bank link couldn't place (the 32 KB may be full or split by a pinned section, so it claims no total size) beside the sections past bank 1 (`BuildMade.overflow`), or leads with the one-bank link's own error (a ROMX bank past 1, an overlap, an undefined symbol); after a full bank 0 or an oversized section the first link wrote no ROM, so the header is unknown, and the first link's error leads (a full bank 0's with a `diagnostics/hints.rs` remedy that claims no total size; an oversized section's row names no file and gets the generic remedy) unless a one-bank error is true whatever the layout (an allow-list: an undefined symbol), and every other one-bank row follows as a warning that names the one-bank link and says it may hold only if the header names no MBC (an error true in any layout but off the allow-list lands there too); with every diagnostic as a file, line and message (a message repeated line after line is one, with its last line and count; `diagnostics/hints.rs` gives a remedy for messages that don't say their fix);
    `doctor`'s checks.
    `BuildOptions.cwd` is the caller's working directory: a relative `out` is read against it, while `src` and `include` are read against the project, so the CLI's positional DIR names the project only and `--dir` (which moves the working directory) moves all three.
  - **The starter:** `new` scaffolds a project (vendored hardware.inc, hUGEDriver and a player for `assets/music/theme.song`, and a text renderer, `src/text.asm`, with a font drawn for gbcli, `assets/fonts/main.yaff`, drawing one line into a 20-tile line buffer, tiles 236-255) with its own `.gbcli/`, so sessions run inside it stay there even under another project's.
    Its `main.asm` claims the restart vectors ($0000-$003F, 64 bytes of `rst $38`), so rgblink can't float a section into them.
    `build --gbc` defines `GBCLI_GBC` for every source, so the starter's color path is assembled only then, and it decides at run time from the boot's A and its own header.
  - **Music:** songs under `assets/music` become hUGEDriver data by convention.
  - **Images:** PNGs (or pixel text, `.pixels`, read through `gbcli-pixels`; a bad one is a `pixels_text` problem with line and column, and a hardware problem on one gives the line that drew the tile; while `assets/palettes.txt` doesn't read, a palette reference that can't resolve is not reported, only the file's own error) in `assets/bg/`, `assets/sprites/` and `assets/tiles/` (tilesets: a background's tiles with no map) are checked against the hardware's limits (structured problems with remedies), encoded by gbcli itself (2bpp tiles, the tilemap, and under `--gbc` the color data and attribute map; `images/encode.rs`, `images/gbc.rs`), previewed, and exposed through a generated `images.inc` and `images.asm` (`gbcli help images`). No tool is run: rgbgfx is only the differential test's oracle ([`project/2026-11-09-rgbgfx-encoder.md`](../project/2026-11-09-rgbgfx-encoder.md)).
    Sheets are 8x16 objects, or 8x8 when a frame size is a multiple of 8 high but not 16, unless the project sets one size for every sheet (the `objects` line of `assets/palettes.txt`, or a manifest's `objects`) (`images/sheet.rs`).
    `images/input.rs` gathers a project's images (or a manifest's, and where its palettes came from, which remedies name) and `images/pipeline.rs` converts them, for `build` and for `assets` (`src/assets.rs`), which runs no toolchain at all (`assets` needs neither RGBDS nor rgbgfx), writes nothing unless asked, and returns the results a build records.
  - **Fonts:** every `assets/fonts/NAME.yaff` (or a manifest's `fonts`) is read through `gbcli-font` (`images/fonts.rs`), never deduplicated, in file order.
    A build emits each font of at most 254 glyphs (or its character list's, `NAME.charlist`, past that; else `font_glyphs`) into the same `images.asm`/`images.inc` as `<Name>FontGlyphs`, `<Name>FontWidths`, constants and a `<NAME>_FONT_CHARMAP name, base` macro (`images/emit/font.rs`);
    `assets` returns the glyphs a request's `glyphs` names, with no cap.
    Both report `FontAsset` in `ImagesMade.fonts` (`gbcli_protocol::font`, the seam LoadHigh reads).
    `src/font.rs` is the `font` op (`gbcli font FILE --sample/--preview/--fit`).
    A letter a request or a character list asks for that the font doesn't draw is composed from its drawn base and mark (`gbcli_font::compose`), after the drawn glyphs, `origin: composed`, with a mark on its base's ink a warning in `ImagesMade.font_overlaps`.
    `src/font_author/` is the authoring ops (`gbcli font edit/save/import/export/new/diff`): it reads and writes the files around `gbcli-font`'s conversions and keeps the working copy in the project's `build/font-edit/` (`copies.rs`), with `NAME.base` recording the font it was made from, which `save` checks before writing (`base.rs`, `save.rs`: the decisions take data); export, guide sheets and diff PNGs never write over a `.yaff` or into that folder (`io.rs`); a build (and `assets`) refuses while a project font's copy is newer than it (`images/fonts.rs`, `find`).
  - **GBC images** (Stage 10, [project/2026-11-07-gbc-images-plan.md](../project/2026-11-07-gbc-images-plan.md)): `build --gbc` writes a dual-mode header; every build, plain or `--gbc`, derives each color image's DMG version (`images/derive.rs`; a `name.dmg.png` overrides it); a session made with `--model gbc` runs it as a GBC.
    `images/pack.rs` packs color art into GBC palettes deterministically;
    `images/gbc.rs` converts color art's GBC tiles behind the one tilemap or frame list both machines share (tiles deduplicated on the pair of versions; `images/output.rs` converts each checked image).
    `images/indexed.rs` gives indexed art (an image `assets/palettes.txt` assigns a palette) its GBC result: its DMG tiles, and a slot in each tile map entry (a sheet's slot holds its palette reordered by its OBP, so slots are keyed by palette and OBP).
    `ImagesMade.dmg_palettes` is each named palette as a BGP byte by the project's shade rule (`Shading::palette_byte`): an art color's own shade, else what the rule makes of it, clamped to the art's range under the stretch, so a palette and the art can't disagree. `assets` returns them even with no images; a build with no images still reports none.
    `images/emit/gbc.rs` writes the labels (`*TilesGbc`, `*Attrmap`, `*Palettes`, `ObjPalettesGbc`, every named palette as `Palette<Name>`, and each indexed sheet's swap copies `<Sheet>Palette<Name>`), and `images/preview.rs` draws a `.gbc.preview.png` in screenshot colors.
- **`crates/pixels` (`gbcli-pixels`)**: pixel text, images as text an agent can write and read (`.pixels`, `format gbcli-pixels 1`; [project/2026-11-08-pixel-text-design.md](../project/2026-11-08-pixel-text-design.md)): the parser (blocks painted in file order, parse errors located to line and column), the canonical writer (rows by frame or 8-row band, or `--tiles`: tiles keyed in hex by first use and a map), PNG decode and encode, the legend a PNG's colors get (`.` clear, then lightest first) and a 4x preview with an 8x8 grid.
  `PALETTE N` and `dmg N` resolve through a `Palettes` the caller reads;
  `gbcli-build`'s `pixels` (the `pixels` op and `gbcli pixels`, `gbcli help pixels`) reads them from the project's `assets/palettes.txt` or `--palettes`.
- **`crates/font` (`gbcli-font`)**: pixel fonts ([project/2026-11-09-pixel-fonts-design.md](../project/2026-11-09-pixel-fonts-design.md), Ben's decisions): gbcli's own strict-subset YAFF reader and writer (`yaff::syntax` reads all of YAFF 1.0, so a file outside the subset is refused for what it is at its line; `yaff::strict` holds it to gbcli's rules; the writer is canonical), keys (`Key`: a character, a code point or a name; `<name>` in a charmap), NFC keys by the protocol's mark table (`gbcli_protocol::marks`: a decomposed key the table knows is refused naming its precomposed letter), the layout rules (`layout::RULES`, which `gbcli help fonts` prints verbatim, and `set`/`draw`, the reference `gbcli font --sample` uses) and previews.
  The authoring conversions are here too, data in and data out (no files, so they build for a web target): the PNG working copy's grid and its `.chars` sidecar both ways, with guides and every disagreement a `Problem` naming its cell (`grid`, `chars`), BDF out and in, trimmed glyphs placed by bounding box and ascent (`bdf`), composition (`compose`), a glyph-by-glyph diff and its picture (`diff`), the named character sets (`sets`) and a 3x5 label font for the guide sheet and the diff (`labels`).
  Tested against two of monobit's published samples, vendored with their licenses in `crates/font/data/monobit/` (`SOURCE`).
- **`crates/music` (`gbcli-music`)**: hUGETracker songs: `.uge` v0-v6 read and v6 written, a canonical tracker-grid text form both ways with parse errors located to line and column (on input a block may name fewer than four patterns, `=` for one another block shows, so a shared pattern is written once: `text/grid.rs`), a piano roll drawn from a song file, and the song to RGBDS `.asm` emitter, a port of hUGETracker's export, departing from it where channels of different kinds share a pattern: their instruments and waves count for each kind, where hUGETracker's export counts only the first channel's and leaves a wave or noise channel playing garbage (`gbcli song`, `gbcli help music`).

## Adapters

- **`crates/server` (`gbcli-server`)**: request handling over the library crates (`break`, `watch` and `delete` resolve against the ROM on disk without loading the head, so a rebuild doesn't block them: `Need::Rom`), screenshots, VRAM, OAM, palette and memory views (`view memory`, `handle/memory.rs`), the per-frame OAM log (`run --oam-log`), key input on runs, `run --expect` (conditions at the stop beside the reads; one false fails the run with `predicate_false`, the run saved and its result on the error: `handle/run/expect.rs`), and the JSONL stdio server (`gbcli serve`).
  A request's relative file paths (shots, PNGs, WAVs, `.sav`s, a build's) start at its `Host`'s working directory: the CLI's, which `--dir` moves.
  - **The library entry point:** `Handler::new(host, bundle, interrupt)`, then `Handler::with_defaults(session, actor)` and `Handler::handle(&Request)` per request: the protocol is the one interface, and the handler reads nothing from the process. `Host::new(cwd, files)` refuses a relative working directory (so a relative request path never silently starts at the project instead); the CLI builds it from its `Env`, refusing a relative one with `io_failed`. `files` (`HostFiles`, `handle/host.rs`) says whether a request may reach the host's own files: `Allowed { path }` (the CLI and `serve`, with the `PATH` RGBDS is found on) or `Denied` (a memory store's caller). The ops that go to the filesystem directly rather than through the store, or run a program (`build`, `doctor`, `new`, `assets`, `pixels`, `font` and the font authoring ops; `reaches_host_files` names every op, so a new one must be placed), are refused on a denied host with `unsupported` before they touch anything, by the `Handler` and `Tooling` alike; everything else (every session op, `sessions`, `gaps`, `prune`, `rm`, `opcode`, `version`) reads and writes only through the store. The interrupt (`interrupt.rs`) is armed per request with its allowance (`wall_guard_s`, else 60 s) and returns the flag emulation polls: natively the caller passes a `Watchdog` (`watchdog.rs`), the thread that sets it when the allowance runs out, which the CLI and `serve` start (refusing the request with `internal` when it won't start natively; on wasm32 falling back to a flag nothing sets); a caller with no thread passes an `InterruptFlag` and sets its flag to stop the request in flight, a zero allowance still stopping at once. Arming clears the flag, so a caller sets it only once the request is running. `Interrupt::stopped_by` says who set it (`StoppedBy`): the guard's answers `wall_guard`, naming the allowance and `--wall-guard` (stop reason `wall_guard`), and the caller's answers `interrupted`, saying the caller stopped it (stop reason `user_break`; the CLI and `serve` never set the flag, so they never answer it), in run, step, the audio replays, measure, equiv and the boot run alike (`run/budget.rs`, `Interruption`). No protocol op creates a session: a caller opens one with `Bundle::open_session` before its first request, as the CLI and `serve` do. `Bundle::start_session` does the same and returns, when it created the session, a `SessionCreated` (`crates/bundle/src/created.rs`): its name, model and ROM's CGB flag, the bundle directory it went into (`Bundle::root`, absolute; under a memory store, the store's virtual project path joined with the bundle, the path every other message names, so the field is always present), and `SessionNote::ColorRomOnDmg` when no model was named and a dual or CGB-only ROM starts as a DMG (`color_note`). The caller hands it to `Handler::with_session_created`, which carries it on the next response as `session_created`: `Handler::handle`'s, or under `serve` the first response written whatever answered it (a line that doesn't parse, a panic), through `Answer::take_session_created`; with no request lines nothing is written. The CLI prints it as the `session_created` row, and the note as a `note color_rom_on_dmg` row with the remedy `SessionNote::remedy` words, so every client says the same. The worked example, with the construction a library caller needs step by step and what a memory caller can and cannot do, is `crates/server/tests/library_caller.rs`: a `MemoryStore` seeded with a test ROM over a real, empty directory, a host that denies host files, and a session driven through run with keys, read, shot (its PNG read back from the store), checkpoint, restore and undo, `new` refused, and the directory still empty.
- **`crates/cli` (`gbcli-cli`)**: argv to protocol requests, answered in-process by the server's handler; rows or `--json` (the serve response line), where any per-frame or per-event list prints a summary or at most 20 rows in text and every item in `--json` (`render::row::capped`; guarded by `render/bounded_tests.rs`; the summaries' groupings, such as `FrameBudgetMade::lag_runs`, are methods on the protocol types; design §12, "bounded rows"); the primer, `--help`, help topics, recipes and the schema.
  `--raster` text is one budget of at most 64 lines: 20 writer rows and a `more` row adding up the hidden writers' risky writes, then a 40-row timeline (`render::profile::RASTER_TIMELINE_ROWS`).
  Every server op is a verb;
  `gbcli --help` lists them, and `crates/cli/src/verbs/` holds the table.
  The help is public as `gbcli_cli::help`, for a library caller with no argv, `Env` or process: `primer()`, `verb(Verb)`, `Topic::text()`, `RECIPES` and `SCHEMA`, with `Verb` and `Topic` looked up by name (`from_name`) or listed (`Verb::all()`, `Topic::ALL`); the CLI prints exactly these strings (`crates/cli/tests/help.rs`).
  It stays in this crate rather than a crate of its own because the verb table it renders lives here, and the crate already builds for `wasm32` and links into the web spike; a help crate is only worth splitting off for a caller that can't take `gbcli-cli` as a dependency.
  Everything else in the crate stays private: the verb table's `VerbSpec`, `FlagSpec` and `Class` aren't public, so the table can change without breaking a caller.
- **`crates/gbcli`**: the binary, and the CLI's golden transcripts (`tests/cli/`).
