# DX: building Lanternfall (the roguelike, D) with gbcli

The developer-experience notes of the agents building `examples/rogue/` as gbcli users, written blind (no other game's DX doc read). One dated section per session, stumbles ranked by cost. Binary: `/Users/ben/.cache/gbcli-examples/target/release/gbcli`, built from main at `c38cd29`; RGBDS 1.0.4 from `PATH`.

## 2026-11-09 — Rogue 1: seeded generation and the scrolled map (agent rogue15)

**What I built.** *Lanternfall*: a lantern-bearer descending a seeded dungeon. A 64x48 map in WRAMX (bigger than the 32x32 background), rooms placed at random without touching and chained by L-shaped corridors (so every floor cell is reachable by construction), stairs in the room farthest from the start, a 16-bit xorshift seeded from the title-screen frame on which START is pressed, and a camera that streams one row or column into the background ring per step from the VBlank handler. Floor changes keep the LCD on and the music playing: palettes go dark, generation yields at line 80 of every frame, the 19 view rows stream in one a frame, palettes return.

**Commands that prove it** (from `examples/rogue/`, gbcli on `PATH` or `GBCLI=/path/to/gbcli` set for the tool):

- Connectivity for several seeds, from the map read out of WRAM:
  `python3 -I tools/maptool.py seeds 20 57 101 160 233 400 1000` → 7 rows `ok … floor=N reachable=N stairs_reachable=True`. A deliberately broken map (two floor cells added out of reach) makes `maptool.py check` print `FAIL … 2 unreachable` and exit 1, so the check can fail.
- One seed, one dungeon: two sessions pressing START on frame 57 (one also mashing A and B on the title) dump byte-identical 3,072-byte maps; frame 58 gives seed 52 and a different map:
  `gbcli run build/rogue.gb --session same-a --frames 120 --keys 'START@57 -START@59'`
  `gbcli run build/rogue.gb --session same-b --frames 150 --keys 'A@10 -A@12 B@30 -B@40 START@57 -START@59'`
  `python3 -I tools/maptool.py dump --session same-a --raw build/same-a.bin` (and same-b), `cmp build/same-a.bin build/same-b.bin` → silent, shasum `e201ace0…` both.
> **Correction (Rogue 2, same day):** `test/descend-seed51.keys` was recorded on Rogue 1's ROM and is gone: Rogue 2 added enemies (a blind walk now meets them) and startup work, so START on frame 57 gives seed 50, not 51, on today's plain build. The seed is the count of frames on the title screen, and key files count frames since boot, so any change to startup time shifts which seed a key file reaches. Rogue 2's recorded win (`test/win-seed50.keys`) covers the same claims: walks, four floor changes, `lag=0`.

- A walk through four floor changes, no lag: `maptool.py descend --session walk --floors 4 --keys-out test/descend-seed51.keys` is a closed-loop bot (reads the floor, BFS to the stairs, walks it, checks the background against the map halfway: `view ok … mismatched=0`), and its recorded keys replay in one run:
  `gbcli run build/rogue.gb --session replay --frames 1300 --keys-file test/descend-seed51.keys --frame-budget --read '[wDepth]'` → `[wDepth] value=4`, `frame_budget frames=1300 lag=0 lcd_off=6 active_max=61884 busiest=573` (the 6 LCD-off frames are startup). Same on `--model gbc` with `gbcli build --gbc`.
- Generation time: `gbcli measure GenerateFloor..GenerateFloor.done --session gen --keys 'START@7 -START@9'` (from a title-screen checkpoint) → 284,788 T wall time, 4.06 frames; `gbcli run --at title --frames 14 --keys 'START@7 -START@9' --profile` puts the CPU work at about 199,000 T (2.8 frames, ~48 ms) once the yields' halts are taken out. A whole floor change, dark to lit, is `measure NewFloor..NewFloor.drawn` → 1,686,808 T, 24 frames (0.4 s).

**Where gbcli helped (saved real time).**

1. **`gbcli new` + `.pixels` + `palettes.txt` worked first time.** The starter built, the indexed tileset and sprite converted, and `build --gbc` was clean with the stock GBC detection. The `shared_shade` warning named the exact two colors and the remedy; one palette tweak fixed it.
2. **`--frame-budget` found a real bug in one run.** My first replay said `lag=1 … frame_cost index=60 active_t=70208 idle_t=0`; a two-frame `--profile --frame-budget` from frame 59 showed six rooms' carving in one frame: my yield threshold (line 100) was too late. Fixed to line 80, `lag=0`. Without the per-frame row I would not have known which frame to look at.
3. **`--profile` sized the first generator honestly.** The first version took 627,876 T (8.9 frames) with the LCD off; `--profile --top 12` showed `MarkWalls` 366k T and `FillMem` 164k T, the two things to rewrite. Five minutes from "slow" to "why".
4. **`rom_changed` is a good error.** After a rebuild it listed every moved symbol and the exact remedy (`--from boot`).
5. **Deterministic runs + carried keys** made the closed-loop bot trivial; replaying its recorded keys from boot reproduced the walk frame for frame.

**Stumbles, by cost.**

1. **No block memory read (~20 min).** The leaf asks for "the map read out of WRAM (`--read` or a memory view)". There is no range form: `gbcli read 'wMap..wMap+16'` → `unknown_symbol: unknown symbol "wMap..wMap"`; `gbcli schema` has no length field on `read`; `view` covers only VRAM maps, tiles, OAM and palettes. I worked around it by passing 3,075 expressions (`[wMap+0]` … `[wMap+3071]`) to one `gbcli read --json` and parsing `reads[].value`. It works (one process, under a second) but it's a hack every memory-dump user will reinvent. Wanted: `gbcli read 'bytes[wMap, 3072]'` or `gbcli dump wMap 3072 --out map.bin`.
2. **The worktree guard refuses `PATH=…:$PATH cmd` and any command line containing a `$G` shell variable (~10 min).** The brief said to put the pinned binary's directory first on `PATH` in each call; the harness refused it as "names git in a form too complex to verify" (the path contains `/git/`). Not gbcli's fault, but it cost time: the tool takes `GBCLI=/abs/path` instead, and every call names the binary by absolute path.
3. **A run stops at VBlank's start, before the handler runs (~10 min).** `gbcli run --frames N` stops with `pc=$0040 symbol=VBlankVector ly=144`, so the frame's VBlank work (my scroll write and row stream) hasn't happened: my view check failed with `scroll=24,0` against a camera at 36 (expected 32). `run --frames 1` more fixed it. Reasonable once known; `gbcli help time` or the `run` help could say "a frame budget stops as VBlank begins, before its interrupt runs".
4. **`--profile` charges halt time to a tail-caller (~5 min).** `MaybeYield` ends in `jp WaitFrame`, and the profile showed `MaybeYield exclusive_t=75204` for 17 calls of a 6-instruction routine: the halts inside the tail-called `WaitFrame` landed on it. Subtracting by hand from `idle_t` worked, but an `idle_t` column per routine would have saved the arithmetic.
5. **The recipe "it records each key change" reads as if gbcli records them (~3 min).** It's the script that records; `run --json` doesn't echo applied keys. Wording, not a bug.
6. **Errors print twice under `--json`** (a text line on stderr and the JSON object on stdout). Harmless when parsing stdout only.

**Missing.** A block read (stumble 1). Nothing else blocked.

**`gbcli gaps`:** `none`.

## 2026-11-09 — Rogue 2: the descent (agent rogue15)

**What I built.** Turn-based play on Rogue 1's floors: a D-pad press steps or attacks (bump-to-attack), B waits a turn, then every enemy acts. Enemies: rats (3 HP, bite 1) and, from floor 3, ghouls (6 HP, bite 2), 2 + depth of them a floor; one next to the player bites, one within 9 cells (x + y) steps toward the player along the longer axis first, else the shorter, never into rock, walls, the player or another enemy. Items lie on the map as cells: a potion each floor (two from floor 3; heals 8), the blade on floor 2 (attack 2 -> 4). Five floors; the fifth has the Ember instead of stairs, and taking it wins. 0 HP ends the run. A window-layer status line (`HP 20/20 ATK 2 FL 1`) in a generated 5x7 font (`tools/font.py` -> `assets/tiles/font.pixels`), and end screens in the window. Placeholder art, all `.pixels`.

**Commands that prove it** (from `examples/rogue/`; tools take `GBCLI=/abs/path/to/gbcli` or find gbcli on `PATH`):

- The win, by a closed-loop bot and its replay. `maptool.py play` reads the floor once and the player, HP and the eight enemies every turn through the run's own `--read`s (one `gbcli run --frames 4 --keys 'RIGHT@1 -RIGHT@3' --read …` per turn), fights what's adjacent, drinks when HP <= 14, takes the blade, and walks to the stairs (around enemies if it can):
  `gbcli run build/rogue.gb --session win --frames 120 --keys 'START@57 -START@59'`, then
  `python3 -I tools/maptool.py play --session win --mode win --keys-out test/win-seed50.keys` -> `won after 632 turns at depth 4 hp=18 frame=2808` (6.5 s of wall time for 632 gbcli calls).
  Replay from boot: `gbcli run build/rogue.gb --session replay-win --frames 2900 --keys-file test/win-seed50.keys --frame-budget --read '[wGameState]' --read '[wDepth]'` -> `[wGameState] value=1` (won), `[wDepth] value=4`, `frame_budget frames=2900 lag=0 lcd_off=8` (6 startup frames, 2 for the end screen's redraw).
- The death: `maptool.py play --session die --mode die --keys-out test/die-seed50.keys` (walk to the nearest enemy, then only wait) -> `dead after 33 turns at depth 0`; replay `gbcli run build/rogue.gb --session replay-die --frames 400 --keys-file test/die-seed50.keys --frame-budget --read '[wGameState]'` -> `value=2`, `lag=0`.
- No lag on the busiest floor (floor 5: six enemies, ghouls among them, chasing): `python3 -I tools/budget.py --from 1713 -- build/rogue.gb --session busy2 --frames 2810 --keys-file test/win-seed50.keys` (frames 1713 on are floor 5 of the win replay; `gbcli run --until '[wDepth] == 4'` found frame 1673, plus 40 for the floor to stream in) -> `frames=1097 lag=0 active_max=18888` (27% of a frame). An enemy turn with all six idle: `gbcli measure EnemiesTurn..PlaceEnemySprites --at floor5-ready --keys 'B@1 -B@3 …' --iterations 4` -> 3,828 T.
- The GBC build: `gbcli build --gbc --out build/rogue-gbc.gb` (errors=0 warnings=0), and the same bot wins on it on a GBC: START on frame 59 there gives seed 51; `maptool.py play --session gbcwin --mode win --keys-out test/win-gbc.keys` -> `won after 453 turns`; replay `gbcli run build/rogue-gbc.gb --session gbcwin-replay --model gbc --frames 2200 --keys-file test/win-gbc.keys --frame-budget --read '[wGameState]'` -> `value=1`, `lag=0`.

**Where gbcli helped (saved real time).**

1. **`run --read` in the same call as `--keys` made the bot one process call per turn.** A 632-turn game plays in 6.5 s. This is the single best thing in gbcli for a turn-based game: the bot is 60 lines of Python, and its recorded keys replay frame for frame from boot.
2. **`--until '[wDepth] == 4'`** found the frame a floor starts on in one call (`stop predicate … frame=1673`), which is what made a per-floor frame budget possible.
3. **The build's errors on a `.pixels` mistake were exact.** `color # stone 0` -> `problem limit=pixels_text … line=5 column=1 message="color takes a legend character and a value"`. The help says `#` isn't a legend character; I'd missed it, and the error put me on the line.
4. **`gbcli build --gbc --out build/rogue-gbc.gb`** keeps both ROMs (and their .sym) side by side, so DMG and GBC sessions don't trip `rom_changed` on each other.

**Stumbles, by cost.**

1. **A key file is tied to the build's startup time (~20 min).** The plain and `--gbc` builds of the same source reach different seeds from the same `START@57` (50 vs 49 on a GBC): the `--gbc` build's color setup takes LCD-off frames before the title counts. Worse, I didn't notice for a while because I had run `gbcli build --gbc` over `build/rogue.gb`, so "DMG" sessions were running the GBC build in DMG mode (seed 50 again, by luck of timing). My game's fault, not gbcli's (the seed is a frame count), but gbcli made it easy to miss: a session created from `build/rogue.gb` doesn't say which build it was, and the build row's `target=gbc` is the only trace. Fixed by building the GBC ROM to its own path (`--out`) and recording a GBC key file. Wanted: `gbcli run` printing the header's GBC flag, or `show` naming the ROM's build target.
2. **`--frame-budget` can't be limited to part of a run (~10 min).** I wanted "no lag on floor 5" out of a 2,900-frame replay; the summary covers the whole run, and the per-frame JSON has no frame numbers (just an array from the run's start). I wrote `tools/budget.py` to slice the JSON. A `--budget-from FRAME` (or checkpoint, with the keys continuing) would do it; alternatively, a run that starts `--at` a checkpoint can't continue a keys file recorded from boot (`keys_unapplied`), which is why I couldn't just run from a floor-5 checkpoint.
3. **A failed image doesn't fail the build row (~3 min).** With the `.pixels` error above: `images converted=0 errors=1` then `build rgbds=1.0.4 target=dmg sources=10 errors=0 warnings=0`. The help explains the split ("the build row counts toolchain diagnostics only"), and the exit code was the tell, but `errors=0` on the last line reads as success.
4. **`gbcli read` has no block form (carried from Rogue 1)**; `maptool.py dump` still sends 3,075 expressions.

**Missing.** A frame-range budget (stumble 2); the ROM's build target in `show`.

**`gbcli gaps`:** `none`.

## 2026-11-09 — Rogue 3: art, music and sound (agent rogue15)

**What I built.** A title screen (`tools/title.py` -> `assets/bg/title.pixels`: a lantern on a chain, its light falling off in Bayer-dithered rings, the name at twice the font's size; 143 unique tiles, loaded over the dungeon's tiles while the title shows and swapped out with the LCD off on START). Sprites split into two indexed sheets so the GBC colors them apart: `hero.8x8.pixels` (palette lantern, GBC OBJ palette 0) and `foes.8x8.pixels` (rat and ghoul, palette blight, OBJ palette 1 through OAM attribute bits 0-2, which the DMG ignores). Dungeon tiles gained a potion, the blade and the Ember. Five palettes in `assets/palettes.txt`, each ordered light to dark under one pinned `dmg:` line, so the DMG build is the same four shades everywhere. Two songs as gbcli song text, both leaving channel 2 empty: `title.song` (D dorian, bell lead, wave hum, ticks) and `dungeon.song` (A minor, slower). Five sound effects on channel 2 (step, hit, hurt, pick-up, stairs) from a small step-list player in the VBlank handler; channel 2 is also muted in hUGEDriver (`hUGE_mute_channel`) so the driver never touches it.

**Commands that prove it** (from `examples/rogue/`):

- Images: every file under `assets/` is `.pixels` or `.song` (`find assets -type f`); the two generated ones regenerate byte-identical: `shasum assets/bg/title.pixels assets/tiles/font.pixels > build/art.sha; python3 -I tools/title.py; python3 -I tools/font.py; shasum -c build/art.sha` -> `OK` twice.
- Music and effects in the audio views, over the whole recorded win: `gbcli run build/rogue.gb --session audio --frames 2900 --keys-file test/win-seed50.keys --audio-summary` -> `NR21 writes=667`, `NR22 writes=1276` and every channel-2 writer PC inside `SfxVBlank` ($00AB-$00E0 by `gbcli sym 'Sfx*'`) but hUGEDriver's two init writes; channels 1, 3 and 4 written by the driver (`NR10-14 writes=91`, `NR30-34`, `NR41-44`, wave RAM twice: one per song start).
  `gbcli run build/rogue.gb --session audio --from boot --frames 260 --keys-file test/win-seed50.keys --audio-log --audio-channel 2` -> the step effect: `NR22 $31: square 2 envelope 3 down, pace 1`, `NR24 $85: square 2 trigger … (180.04 Hz)`, every 4 frames as the player walks.
  `… --frames 260 --piano build/audio/short.png --scale 1`: the title theme's lead and bass, the switch to the dungeon theme at START, and the step blips on square 2 at the right edge. `--wav build/audio/opening.wav --channels each` writes one WAV per channel.
- Both builds, with the art: `gbcli build` and `gbcli build --gbc --out build/rogue-gbc.gb` -> `errors=0 warnings=0`, images `converted=5 errors=0 warnings=0 shades=declared`. The win replays on both: `gbcli run build/rogue.gb --session rw3 --frames 2900 --keys-file test/win-seed50.keys --frame-budget --read '[wGameState]'` -> `1`, `lag=0`; on a GBC the same seed (START on frame 59 there) gives the same game, turn for turn: `maptool.py play` -> `won after 632 turns at depth 4 hp=18` on both models.

**Where gbcli helped (saved real time).**

1. **`gbcli song FILE` as a checker.** My title song's second block copied the channel 2-4 patterns wrong; it said `pattern P2 differs from its copy in the block at line 34, at row 56` with the fix. Under a minute.
2. **`--audio-summary`'s writer PCs** proved the channel split in one run: every NR21-24 write came from my effect player, none from the driver after init. That is exactly the claim the leaf asks for, in one command.
3. **Indexed `.pixels` + named palettes + the `dmg:` line** made the GBC colors a data change: a second sprite palette was two lines of `palettes.txt` and one OAM bit. `view palettes` confirmed OBJ palette 1 held the blight colors.
4. **`--piano --scale 1`** is a readable picture of 4 seconds of audio; the default scale 2 over 900 frames is 7,194 px wide, too wide to look at.

**Stumbles, by cost.**

1. **One bad line in `palettes.txt` turns into six errors (~5 min).** A stale `sprites/actors.8x8.pixels = lantern` line (I'd deleted that sheet) gave the right error, plus `no palette ember/blight/lantern/stone: the palettes define none` for every image, as if the whole file were gone. The first error was correct and its remedy good; the other five sent me looking at palette names that were fine.
2. **`audio_writer` rows have a PC but no symbol (~3 min).** `--profile` and stop rows name symbols (`symbol=VBlankVector`); `--audio-summary`'s `audio_writer pc=$00C5` doesn't, so I ran `gbcli sym 'Sfx*'` and compared addresses by hand.
3. **The piano roll draws a silent channel's retrigger** (hUGEDriver's mute writes `NR22 $00` then `NR24 $FF`) as a dim dashed note at 512 Hz for the whole title. It's honest (the channel was triggered) but read as a stuck note until I checked the audio log.
4. **Key files keep breaking as startup changes (carried from Rogue 2, ~5 min).** The title screen's 2.3 KB of tiles load with the LCD off, so START on frame 57 now reaches the title 10 frames later; the seed stayed 50 by luck of where the count starts, but every recorded file needed re-recording. The bots make that cheap (one command each); it's the game's design (a frame-count seed), not gbcli.

**Missing.** Symbols on `audio_writer` rows.

**`gbcli gaps`:** `none`.

## Summary: the whole game (Rogue 1-4)

Four leaves by one agent, about 35% of a 1M context. gbcli never blocked the game; every stumble had a workaround inside an hour, most inside ten minutes.

**The five costliest stumbles.**

1. **No block memory read (Rogue 1, ~20 min, and every map dump since).** "Read the map out of WRAM" has no direct command: no range form in `read` (`'wMap..wMap+16'` -> `unknown_symbol`), no length in the schema, and `view` covers only VRAM, OAM and palettes. The workaround (3,075 expressions in one `gbcli read --json`) works and is fast, but it's the first thing anyone checking generated data will hit. Fix: `gbcli read 'bytes[wMap, 3072]'` or a `dump` verb writing a .bin.
2. **Recorded key files are tied to the build's startup time (Rogue 2-3, ~25 min in all).** My seed is the title-screen frame count, key files count frames since boot, and the plain and `--gbc` builds (and every startup change) reach the title on different frames. I made it worse by building `--gbc` over `build/rogue.gb` and testing the wrong ROM in "DMG" sessions without noticing. The game's design, not a gbcli bug, but gbcli could make it visible: nothing in `show` or a stop row says which build (target, header GBC flag) a session runs.
3. **The frame budget covers a whole run only (Rogue 2, ~10 min).** "No lag on floor 5" needed a slice of a 2,900-frame replay; the summary can't be limited, the per-frame JSON array has no frame numbers, and a run `--at` a mid-game checkpoint can't continue a keys file recorded from boot (`keys_unapplied`). I wrote `tools/budget.py` to slice the JSON. Fix: `--frame-budget-from FRAME`, or frame numbers in the JSON.
4. **A frame budget stops as VBlank begins, before the handler runs (Rogue 1, ~10 min).** A view check right after `run --frames N` saw last frame's scroll registers (`pc=$0040 symbol=VBlankVector ly=144`). One extra frame fixed it; one sentence in `run --help` or `help time` would have saved the confusion.
5. **The harness refused `PATH=…:$PATH cmd` (Rogue 1, ~10 min).** The brief said to put the pinned binary's directory first on `PATH`; the worktree guard refused it ("names git in a form too complex to verify", the path contains `/git/`). Not gbcli's fault; my tools take `GBCLI=/abs/path` instead and every call names the binary by absolute path.

Runners-up: one bad `palettes.txt` line cascading into six errors (Rogue 3); `--profile` charging a tail-called `WaitFrame`'s halts to the caller (Rogue 1); `audio_writer` rows with PCs but no symbols (Rogue 3); `images errors=1` above `build … errors=0` (Rogue 2).

**The three things that helped most.**

1. **Deterministic runs with `--keys` and `--read` in one call.** A closed-loop bot is one `gbcli run --frames 4 --keys 'RIGHT@1 -RIGHT@3' --read …` per turn: a 632-turn game in 6.5 s of wall time, recorded keys that replay frame for frame from boot, and the same seed playing the same 632-turn game on a DMG and a GBC. Every proof in the README rests on this.
2. **`--frame-budget` plus `--profile`.** The budget named the one lag frame (`frame_cost index=60 … idle_t=0`) and a two-frame profile from there showed why (six rooms carved in one frame); earlier, `--profile` turned an 8.9-frame generator into two named rewrites. Measure-then-fix took minutes each time.
3. **The asset pipeline as text: `.pixels`, `palettes.txt` with a `dmg:` line, and song text.** Art and music are files an agent writes and diffs; the build checks them against the hardware with exact, located errors (`line=5 column=1`, `pattern P2 differs … at row 56`), and `build --gbc` colored the game from the same files with two extra palette lines. `--audio-summary`'s writer PCs then proved the music/effects channel split in one command.
