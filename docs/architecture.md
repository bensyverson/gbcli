# Architecture

Which crate owns what. gbcli is a Rust workspace: library crates hold every decision, `gbcli-server` and `gbcli-cli` are thin adapters over them, and the `gbcli` binary only wires argv, the environment and stdio into `gbcli-cli`. The approved design behind this is [project/2026-11-06-design.md](../project/2026-11-06-design.md).

Add a crate or a major capability here when you build it; keep the head of `AGENTS.md` free of feature lists.

## The emulator

- **`crates/core` (`gbcli-core`)**: the `Core` trait, our own seam over any emulator backend, and its types (`CoreConfig`, cart clocks, flash notes).
- **`crates/sameboy-sys`**: vendored SameBoy, built by the `cc` crate, with hand-written FFI and the small C accessors in `shim/`. The vendored commit, compile flags and patches: [project/2026-11-06-sameboy-vendoring.md](../project/2026-11-06-sameboy-vendoring.md).
- **`crates/sameboy` (`gbcli-sameboy`)**: the SameBoy backend implementing `Core`: bank-aware filters, never-written tracking, the checkpoint blob, and a flash chip on flash-save carts.
- **`crates/flash` (`gbcli-flash`)**: an AMD/JEDEC flash-chip model for flash-save carts such as GB Studio's batteryless saves, parameterized by board (unlock addresses, D0/D1 swap, sector map, /WE pin, chip size, busy times) with named profiles from FlashGBX's database; commands that miss the board become `FlashNote`s, and mask-ROM programs that send flash commands get a hint. A session takes a board with `--flash BOARD` (`gbcli help flash`; [project/2026-11-07-flash-model.md](../project/2026-11-07-flash-model.md)).

## The engine and the session

- **`crates/engine` (`gbcli-engine`)**: inspection, the disassembler and `gbcli opcode`'s lookup (`disasm::lookup`, checked against rgbasm by a seeded differential test), sessions, checkpoints, the debugger (a restart, `run --from boot` or `power-cycle`, moves breakpoints and watches set by a symbol to where a rebuild put it: `Machine::rebase_debugger`), the cycle profiler (`measure`: cycles between two addresses, under a run's key timeline when given one; cycles per routine, named by the `.sym` label at the entry or the hardware vector there (`STAT_vector`), and the per-frame budget, which counts a frame the LCD was off for apart from lag) and the A/B equivalence check (`equiv::compare`: two builds under one key timeline, the first frame whose pixels, chosen RAM or sound-register writes differ, naming a RAM byte a side has never written, so its power-on value is random). Run's `--measure`, `--profile`, `--frame-budget` and `--raster` (IO-register writes by line, each with the PPU mode it landed in, which `crates/sameboy` reads from SameBoy's display state without running it) come from here. `inspect::video` decodes tiles, maps, OAM (with the 10-per-line drops) and the palettes (`palettes`: BGP/OBP0/OBP1, and palette RAM on a CGB) for `view` and `run --oam-log`. `Symbols::containing` picks, among labels at one address, any but an end marker (`TilesEnd`, `end_zero`), since the `.sym` alone can't say which section a label ends.
- **`crates/protocol` (`gbcli-protocol`)**: the wire types every crate shares: requests and responses, the checkpoint header and stop record, the build and image results, and the named palettes with their one rule set (`NamedPalettes::check`, which the file parser and deserialization both apply). A type crossing the JSONL seam is defined once, here. So is `PROTOCOL_VERSION`, which the `version` op reports and which goes up on any breaking wire change.
- **`crates/bundle` (`gbcli-bundle`)**: the session bundle store (no daemon).
- **`crates/corpus` (`gbcli-corpus`)**: the test-ROM runner and the SameBoy baseline ([project/2026-11-06-sameboy-baseline.md](../project/2026-11-06-sameboy-baseline.md)).

## Views

- **`crates/view` (`gbcli-view`)**: image views as deterministic PNG pinned by goldens: labeled frames, scales and crops, filmstrips, frame diffs, tileset, tilemap and OAM.
- **`crates/audio` (`gbcli-audio`)**: the sound-register write log decoded into notes and settings, WAV export (mixed and per channel), piano roll and spectrograms, pinned by goldens; wired into `run` as `--audio-log`, `--audio-summary` (writes by register and writer PC), `--audio-channel N` (the log and summary narrowed to channels), `--wav PATH [--channels each]`, `--piano PATH` and `--spectrogram PATH`.

## The build loop and assets

- **`crates/build` (`gbcli-build`)**: the RGBDS loop.
  - **Toolchain and build:** RGBDS from `PATH` checked against the 1.0.4 pin; a build by convention with every diagnostic as a file, line and message (a message repeated line after line is one, with its last line and count; `diagnostics/hints.rs` gives a remedy for messages that don't say their fix); `doctor`'s checks.
  - **The starter:** `new` scaffolds a project (vendored hardware.inc, hUGEDriver and a player for `assets/music/theme.song`) with its own `.gbcli/`, so sessions run inside it stay there even under another project's. `build --gbc` defines `GBCLI_GBC` for every source, so the starter's color path is assembled only then, and it decides at run time from the boot's A and its own header.
  - **Music:** songs under `assets/music` become hUGEDriver data by convention.
  - **Images:** PNGs in `assets/bg/`, `assets/sprites/` and `assets/tiles/` (tilesets: a background's tiles with no map) are checked against the hardware's limits (structured problems with remedies), converted by rgbgfx, previewed, and exposed through a generated `images.inc` and `images.asm` (`gbcli help images`). `images/input.rs` gathers a project's images (or a manifest's) and `images/pipeline.rs` converts them, for `build` and for `assets` (`src/assets.rs`), which converts without rgbasm or rgblink, writes nothing unless asked, and returns the results a build records.
  - **GBC images** (Stage 10, [project/2026-11-07-gbc-images-plan.md](../project/2026-11-07-gbc-images-plan.md)): `build --gbc` writes a dual-mode header and derives each color image's DMG version (`images/derive.rs`; a `name.dmg.png` overrides it); a session made with `--model gbc` runs it as a GBC. `images/pack.rs` packs color art into GBC palettes deterministically; `images/gbc.rs` converts color art's GBC tiles behind the one tilemap or frame list both machines share (tiles deduplicated on the pair of versions; `images/output.rs` converts each checked image). `images/indexed.rs` gives indexed art (an image `assets/palettes.txt` assigns a palette) its GBC result: its DMG tiles, and a slot in each tile map entry (a sheet's slot holds its palette reordered by its OBP, so slots are keyed by palette and OBP). `images/emit/gbc.rs` writes the labels (`*TilesGbc`, `*Attrmap`, `*Palettes`, `ObjPalettesGbc`, every named palette as `Palette<Name>`, and each indexed sheet's swap copies `<Sheet>Palette<Name>`), and `images/preview.rs` draws a `.gbc.preview.png` in screenshot colors.
- **`crates/music` (`gbcli-music`)**: hUGETracker songs: `.uge` v0-v6 read and v6 written, a canonical tracker-grid text form both ways with parse errors located to line and column, a piano roll drawn from a song file, and the song to RGBDS `.asm` emitter, a port of hUGETracker's export (`gbcli song`, `gbcli help music`).

## Adapters

- **`crates/server` (`gbcli-server`)**: request handling over the library crates, screenshots, VRAM, OAM and palette views, the per-frame OAM log (`run --oam-log`), key input on runs, and the JSONL stdio server (`gbcli serve`). A request's relative file paths (shots, PNGs, WAVs, `.sav`s, a build's) start at its `Host`'s working directory: the CLI's, which `--dir` moves.
- **`crates/cli` (`gbcli-cli`)**: argv to protocol requests, answered in-process by the server's handler; rows or `--json` (the serve response line); the primer, `--help`, help topics, recipes and the schema. Every server op is a verb; `gbcli --help` lists them, and `crates/cli/src/verbs/` holds the table.
- **`crates/gbcli`**: the binary, and the CLI's golden transcripts (`tests/cli/`).
