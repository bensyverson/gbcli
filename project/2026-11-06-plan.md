# gbcli plan: an agent-friendly Game Boy development tool

2026-11-06. Evidence and the decisions behind it are in [2026-11-06-backend-evaluation.md](2026-11-06-backend-evaluation.md); this doc says what we build, in what order, and why.

> Imported into `job` on 2026-11-06 as root `9b5RBA`. After import the tracker is the plan: change leaves with `job edit`, not this YAML.

## Goal

A homebrew developer hands gbcli to an agent (Sonnet-class or better) with a tight performance goal — "make this arcade puzzler run its main loop in half the cycles" — and the agent iterates quickly and safely: rebuild, restore a checkpoint, run, measure cycles, look at the screen and the audio, compare against the previous build, repeat. Every answer it gets is faithful to DMG hardware (GBC also supported), and the tool teaches just enough Game Boy engineering, through its own help, for the agent to get started without an external manual.

Priorities, in order: **fidelity**, **fast feedback loops**, **debugging and inspection depth**, **onboarding**.

## Architecture

```
  agent in a shell                 harness code (Agent SDK, Python…)
        │ gbcli <verb> …                    │ JSON Lines on stdin/stdout
        ▼                                   ▼
  ┌───────────── gbcli (one Go binary) ─────────────────────────────┐
  │ cli      thin client: verbs, primer, help, exit codes           │
  │ server   JSONL over stdio, or a named session on a Unix socket  │
  │ protocol one set of request/response structs, shared by both    │
  │ engine   sessions · checkpoints · debugger · observations ·     │
  │          profiler · build loop          (Go library; the logic) │
  ├──────────────── core C interface (ours) ────────────────────────┤
  │ shim     ~small C: run loop with budgets, bank-aware address    │
  │          filters, stop records, last-complete frame, taps       │
  │ SameBoy  vendored Core/ at a pinned commit, compiled by cgo     │
  └─────────────────────────────────────────────────────────────────┘
        (later, maybe: a Rust core exporting the same C interface)
```

- **Library + thin executable.** The engine is a Go library; the server and CLI are adapters over it. The engine never prints; the adapters format.
- **The core C interface is ours, designed for the ideal core, not SameBoy's shape.** It includes dot stepping, per-pixel layer identity, side-effect-free reads, a saved emulated-cycle counter. Where SameBoy can't deliver, the shim returns an explicit *unsupported*, never an approximation. A bespoke core would export the same interface, so the harness, CLI and onboarding don't change. Lockstep testing between two cores then costs almost nothing.
- **The per-instruction hot path stays in C.** A Go callback per instruction would roughly halve emulation speed (C→Go callback 38.8 ns measured vs ≈44 ns of SameBoy work per instruction). The shim checks bank-aware address bitmaps and calls into Go only on a match.
- **A daemon, on purpose.** House CLI rules prefer stateless commands over a stateful file; a daemon must earn its keep. The trigger, written down: a named session holds warm emulator instances, in-memory checkpoints (restore measured at 10.3 µs) and debugger state. Re-creating that per command would cost a process start, a ROM load and a state load each time, and would lose breakpoints. Sessions are named, listable and prunable; a bare invocation without a session name leaves no trace.

**Fidelity rules every leaf obeys** (from the evaluation's findings):

1. **Inspection goes through SameBoy's direct access only.** `GB_read_memory` and even `GB_safe_read_memory` change state (open bus, PPU sync, possible DMG OAM corruption). Bus reads exist only as an explicit, labeled operation.
2. **Never drive SameBoy's text debugger.** It blocks, prints unstructured text, perturbs DMG state, and can't watch banked SRAM/VRAM. Our debugger is built on public hooks.
3. **Determinism is a contract.** Fixed RNG seed per instance before `GB_init`, RTC in accurate mode, joypad bounce off unless requested, no host time. The same inputs give byte-identical states; a test pins it.
4. **The checkpoint is an envelope:** SameBoy's state blob plus wrapper-owned state — ROM hash, core commit, model, boot ROM hash, config, emulated cycles, ROM patch set, key state, debugger configuration. Loads verify the envelope first, because SameBoy silently switches models within a family and checks no ROM identity.
5. **Three kinds of write, never conflated:** bus write (as the CPU would, with IO side effects), poke (backing memory, none), ROM patch (bank + offset, recorded in the envelope).
6. **Reject, don't approximate.** Anything the core can't do returns *unsupported* with the reason, and the event is counted in the gap ledger.

## Order and why

0. **Foundations** — scaffold, kick the tires, test corpus, design doc. The design doc waits on the DX note so verbs come from real friction, per the house CLI rules.
1. **Core interface and SameBoy shim** — the fidelity- and speed-critical layer, with numbers pinned as criteria.
2. **Engine** — sessions, checkpoints, debugger, inspection: the Go library.
3. **Server, client and CLI** — the adapters.
4. **Observations** — screenshots, views, audio.
5. **Profiling and verification** — what makes optimization work safe.
6. **Build loop and onboarding.**
7. **Agent eval** — the definition of done for the CLI and onboarding.
8. **Decision on a bespoke core** — scheduled, blocked by the eval.
9. **Cartridges** — mapper verification and the flash-chip model.

Stages 4–6 can overlap once stage 3's protocol is stable; their file surfaces are separate (observations, profiler, build packages).
