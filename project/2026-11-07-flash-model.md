# The flash-chip model for flash-save carts (leaf L00RuF)

2026-11-07. What was built, what the GB Studio validation found, and the one choice left open: how a session names its board.

## What exists

- **`crates/flash` (`gbcli-flash`)**: a backend-free AMD/JEDEC chip (`FlashChip`) driven by a core's memory callbacks, with `FlashProfile` for the board and `FlashNote` for commands that miss it. Design §6, update of this date, lists the behavior. Unit tests: `crates/flash/tests/chip.rs`, the sequences from gbvm's `src/core/gb/flasher_s.s` (chrismaltby/gbvm at `4f01d26`, MIT) and the AMD command set.
- **Named profiles** restate the facts of ten FlashGBX files (lesserkuma/FlashGBX `config/fc_DMG_*.txt` at `5b2398b`; GPL-3.0, so no file is vendored). `scripts/flash/flashgbx-summary.py <FlashGBX>/FlashGBX/config` prints every AMD DMG board's pin, unlock cycles, swap, size and sector map. Across the 93 AMD boards it lists: unlock $0AAA/$0555 on 52 (20 swapped), $0555/$02AA on 20 (7 swapped), $5555/$2AAA on 10, $4AAA/$4555 on 8 (5 swapped), and three rarer variants; /WE on WR 72, AUDIO 21.
- **SameBoy**: `CoreConfig::flash`, the chip on SameBoy's callbacks (`crates/sameboy/src/flash.rs`), the blob's flash section (format 4), `Core::flash_contents` / `load_flash_contents` / `take_flash_notes`. Tests: `crates/sameboy/tests/flash.rs`.
- **Engine**: `Machine` keeps the profile in its setup and `power_cycle` carries the chip's contents.

Assumed, not sourced: the busy times (`BusyTicks::TYPICAL`: 10 µs program, 0.7 s sector erase, 25 s chip erase) and the 2 MiB size of the generic boards, whose FlashGBX files give none.

## The GB Studio validation

Ben exported GB Studio's default project with MBC5 and "Save game data to ROM" (`local/demo/`, gitignored). Header: $1E (MBC5+RUMBLE+RAM+BATTERY), ROM size $02 (128 KiB), RAM $03. `__start_save` is 12 (`demo.map`).

- **The save lands past the image.** gbvm erases and programs banks 12-15, but the file is 8 banks. SameBoy masks the bank by its buffer size, so on the bare image bank 12 is bank 4, which holds code (785 of its 16,384 bytes are $FF): the erase would wipe it. A real cart's chip is larger than the image. So the model pads SameBoy's buffer with $FF to the profile's chip size, and the mapper reaches all of it.

  > **Correction, 2026-11-07 (leaf 6pr1FU):** padding the buffer before SameBoy loaded it also changed the mapper SameBoy chose (an MBC3 over 2 MiB became an MBC30; a ROM-only image became an MBC3). The buffer now grows only after the mapper is chosen from the image; see "Review fixes" below.
- **How the project saves**: the cave's save point (actor at tile 14,11, `project/scenes/cave/actors/actor_6.gbsres`) offers "Save Game / Cancel" and runs `EVENT_SAVE_DATA`; the title screen's "Continue" runs `EVENT_LOAD_DATA` or says "No Save Data Found...". gbvm restores SRAM from flash at start-up (`load_save.c`), so the cart's battery-backed SRAM, which the power cycle keeps, is overwritten from flash and doesn't mask a failed save.
- **The tests** (`crates/engine/tests/flash_save.rs`) drive that by key input: power-on, START, New Game, walk west around the pond, north up column 2, east along row 9 into the cave, up and right to (12,11), A, "Save Game", then a power cycle and "Continue". The player's tile is read from `_actors+2` (x) and `_actors+4` (y), found by walking the player with `gbcli run --keys ... --read`, not from gbvm's source. On `generic-wr-aaa-a9` (swapped, the sequence gbvm hard-codes) the save is programmed into banks 12-15, no notes are taken, and Continue puts the player back at (12,11). On `generic-wr-aaa-aa` nothing is programmed, the first note reads "$0AAA<-$A9 is not an unlock cycle on this board: the chip reads $A9 and expects $AA. $A9 is what a board with D0 and D1 swapped needs ...", and Continue doesn't reach the cave. Disabling the power cycle's flash carry makes the first test fail (checked by hand).
- **Cost**: each test runs about 3,000 frames with the read callback on every access, about 10-12 s alone (`cargo test -p gbcli-engine --test flash_save`, dev profile, Apple M1 under load average 26-38). That is a large share of the 30 s warm budget, so they are in the pre-release suite (`cargo test -p gbcli-engine --test flash_save -- --ignored`; Ben, 2026-11-07).

## Decided: how a session names its board

> **Ruled by Ben, 2026-11-07:** option 1 plus the hint of option 2. `--flash PROFILE` at session creation takes **named profiles only** (no CLI parameter overrides yet; the checkpoint header stores the name). On a flash session, **`sav` and `power-cycle --sav` export and import the flash save area** as well. The two GB Studio tests moved to the pre-release suite. The options as first written follow.


The model is reachable only by building a `CoreConfig` in Rust. Neither the checkpoint header nor the session bundle records a profile, so `Machine::restore` keeps the machine's own and no request can choose one. Options:

1. **A session property, like `--model` and `--seed` (recommended).** `--flash PROFILE` when a session is created; stored in the bundle's meta and in the checkpoint header (a new optional field beside `config`, the profile's name plus any overridden parameters), checked on restore like the model (a conflict is `bad_request`), and kept by `power-cycle`. A board is part of the cart, which a session fixes at creation; this is the existing convention for what the core is built from. Notes surface on the run that took them, as warning rows (`flash_note at= addr= value= text=`) and `--json` fields.
2. **A hint from a mask-ROM session**, in addition to 1: when a run sees a write that is an unlock cycle for some board (the same test `FlashChip` uses), warn "this program sends flash commands; create the session with --flash generic-wr-aaa-a9 to model a flash-save cart". Cheap, and it routes an agent that didn't know to the flag.
3. **Per power cycle** (`power-cycle --flash PROFILE`), to try one save on several boards. Rejected as the primary surface: it changes the cart mid-session, and a checkpoint before it would load into another board. Trying boards is two sessions.
4. **A project file** for the build loop (`gbcli.toml` naming the board). Useful later, as a default for option 1; not a substitute.

Choices inside option 1 that also need a ruling: whether custom parameters are allowed at the CLI (e.g. `--flash generic-wr-aaa-aa,size=4M`) or only named profiles at first; and whether `sav`/`power-cycle --sav` should also export/import the flash save area (a GB Studio batteryless game's save lives there, not in SRAM).

## Review fixes (leaf 6pr1FU)

The independent review of e9cba4f found three low findings; all three are fixed.

- **The mapper came from the padded size.** `SameBoy::new` padded the image to the chip before `GB_load_rom_from_buffer`, and `GB_configure_cart` (`Core/mbc.c`) reads the buffer's length: an MBC3 image on a board over 2 MiB (`mx29lv320et`) became an MBC30 with an 8-bit bank register, and a ROM-only image padded past 32 KiB took SameBoy's "no MBC but over 32 KiB: assume MBC3" fallback. Now SameBoy loads the image itself, chooses the mapper exactly as on a mask-ROM session, and only then does `gbcli_set_rom_size` (`shim/gbcli_shim.c`, our own accessor, no SameBoy patch) grow the buffer to the chip, $FF-filled, without reconfiguring the cart. Every ROM read masks by `rom_size`, so the reach grows and the type doesn't. **A ROM-only cart on a board reaches only its first 32 KiB**: such a board has no bank register, and the CPU's 15 address lines reach 32 KiB, so the chip's upper address lines are fixed; that is what the hardware does, so it is what the model does. An **MMM01** image on a board is refused: SameBoy finds an MMM01's header bank at the end of the buffer, which the chip's erased tail would hide, and a multicart mapper with a flash save is not a board the model knows. A chip size that isn't a power of two is refused. Tests: `crates/sameboy/tests/flash.rs` (`an_mbc3_image_on_a_4mib_board_stays_an_mbc3`, `a_rom_only_image_on_a_board_gains_no_mapper`, `an_mmm01_image_on_a_board_is_refused`, `a_chip_size_that_isnt_a_power_of_two_is_refused`).
- **Command-address decode.** Every profile had `command_mask` $7FFF, so unlock cycles at $4AAA/$4555 matched only with an odd bank mapped. Each profile's mask is now its chip family's (`crates/flash/src/profiles.rs`, constants with the citations), checked against the datasheets:
  - AMD-style parts compare A10-A0 and, in byte mode, A-1, and treat A11 and up as don't-care in command cycles. S29AL016D (Spansion's successor to Am29LV160D; publication S29AL016D_00 rev A amendment 7, 2007), Table 10.1 note 5: "Address bits A19–A11 are don't cares for unlock and command cycles, unless SA or PA required." MX29LV160T/B (Macronix PM0866 rev 3.7, 2003), Table 5 note 3: "AAAH or 555H to Address A10~A-1 in byte mode. Address bit A11~A19=X=Don't care for all address commands except for Program Address (PA) and Sector Address (SA)." Am29DL16xD (publication 21533 rev E, 2004), Table 14 note 5: "Unless otherwise noted, address bits A19–A11 are don't cares." The original Am29LV160D datasheet (publication 22358) was not reachable.
  - So the "AAA" boards (the cart's A0 on the chip's A-1, byte mode), `29dl163bd-90` and `am29lv160db` decode byte bits 11-0: mask **$FFF**. The "555" boards' unlock addresses put the cart's A0 on the chip's A0, so 11 bits: mask **$7FF** (the wiring is inferred from the addresses; FlashGBX doesn't describe it).
  - `mx29lv320et`: the MX29LV320E datasheet (PM1575 rev 1.3, 2013) states no don't-care rule, only the byte-mode addresses AAA/555. Its $FFF is the family's, **inferred, not documented**.
  - SST39SF010A/020A/040 (Microchip DS20005022F rev F, 2025), Table 4-2 note 1: "Address format A14-A0 (Hex), Addresses AMS- A15 can be VIL or VIH, but no other value, for the command sequence": mask **$7FFF**. That is why FlashGBX issues this chip's commands with bank 1 mapped (`flash_commands_on_bank_1`, `LK_Device.py`): $5555 needs chip A14, which comes from the bank register's bit 0.
  - FlashGBX's `am29lv160db` board sends its commands at $4AAA/$4555 without `flash_commands_on_bank_1`; nothing in it says why (likely writes below $4000 reach that board's CPLD mapper). With A11 and up don't-care the bank doesn't matter, which the new test pins.
  Tests: `crates/flash/tests/chip.rs` (`every_profiles_command_mask_is_its_chip_familys`, `commands_in_the_4000_window_work_on_every_bank`), `crates/sameboy/tests/flash.rs` (`unlock_cycles_in_the_4000_window_dont_depend_on_the_bank`).
- **A refused load dropped the chip's notes.** The flash section loaded first, and `FlashChip::load` takes the notes; the rollback after SameBoy refused its own section restored the array and the command state, not the notes. Now the load is two halves, `FlashChip::check_load` (decodes and checks the whole state, changing nothing) and `finish_load`, and `SameBoy::load` finishes the chip only after SameBoy has accepted its section, so a refused load leaves the core exactly as it was, with no rollback. Test: `a_refused_load_keeps_the_pending_notes`.
